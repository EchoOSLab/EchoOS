# 01 · 定位与范围

## 1.1 一句话定位

**EchoOS 是一个用 Rust 从零实现的、类 FreeRTOS 的硬实时操作系统。**

架构参照 FreeRTOS：精简的宏内核 + 清晰的移植层 + 可裁剪的独立组件（对照表见 [02 §2.2](02-embodied-ai-robot-profile.md#22-架构参照freertos--实时控制增强)）。Rust 把 FreeRTOS 里靠约定维持的部分变成编译期保证；**实时控制增强**（零抖动静态调度、抖动可量化、ISR-first 控制环）则是相对 FreeRTOS 的价值增量。

目标场景是**具身智能机器人**，EchoOS 运行在其**小脑层（协调）与脊髓层（关节执行）**。

> **两条重要的范围界定**（2026-09-22）：
>
> 1. **目标场景为具身智能机器人**——不是工业控制、不是汽车 ECU、不是通用嵌入式。场景分析见 [02-embodied-ai-robot-profile.md](02-embodied-ai-robot-profile.md)，该文是**需求基线**，本文中与之冲突的条款以 02 为准。
> 2. **分阶段交付，实时控制优先**（[ADR-0019](05-design-decisions.md#adr-0019--分阶段交付实时控制优先)）。**当前只做阶段一：实时控制内核**。AI 接入属于阶段三，现在只固化架构不变式、不实现。阶段划分见 [02 §2.3](02-embodied-ai-robot-profile.md#23-分阶段交付策略-)。

## 1.2 设计目标

按优先级排序。当目标冲突时，序号小的优先。

| # | 目标 | 说明 | 可度量指标 |
| --- | --- | --- | --- |
| G1 | **硬实时确定性** | 中断延迟与上下文切换时间有确定上界，且**抖动**受严格约束（抖动比绝对值更重要——见 [02 §2.5](02-embodied-ai-robot-profile.md#25-实时需求的量化)） | 中断延迟 P99 < 1 µs；**抖动 P99−P50 < 200 ns**；周期任务触发抖动 < 1 µs |
| G2 | **内存安全** | `unsafe` 面积最小化并集中在少数可审计 crate；UB 由构造消除而非靠约定 | `cargo geiger` unsafe 行数阈值；Miri 覆盖 host 可测部分 |
| G3 | **静态可裁剪** | 未用到的子系统不产生 ROM/RAM 开销，且裁剪在编译期完成 | 最小配置（调度器+trace）ROM < 8 KB、RAM < 2 KB |
| G4 | **可移植** | 体系结构相关代码全部收敛在 `echo-arch-*`；换架构不改内核 | 同一份内核代码在 Cortex-M 与 RV32 上通过同一套测试 |
| G5 | **资源可控** | ⚠️ **已从"极致低资源"调整**：机器人目标平台是 STM32H7（1 MB RAM / 2 MB Flash），不再以 64 KB 级 MCU 为约束。仍要求内核本身精简 | 最小配置（调度器+trace）ROM < 8 KB、RAM < 2 KB；**不含机器人层** |
| G6 | **零外部依赖** | 所有链接进镜像的代码均为自研；不引入任何第三方 crate | `[dependencies]` 中外部 crate 数量 **= 0**（由 `xtask` 强制） |
| G7 | **可验证性** | 为机器人功能安全认证预留路径（IEC 61508 SIL / ISO 13849 PLd / ISO 10218） | 需求→测试可追溯；unsafe 安全契约文档化 |
| G8 | **可调试性** | 死锁、栈溢出、优先级反转、中断风暴能被快速定位 | 内置 shell + trace + 运行时断言 |

## 1.3 明确非目标（Non-Goals）

明确写出来，避免范围蔓延。这些是**首版（1.0 之前）不做**的：

- ❌ **不做 POSIX / Linux 兼容层**（全量）。API 是 Rust 原生的。⚠️ **2026-11-10 修订**：允许一个**可选的、时间分区的 POSIX 子集**（参照 PSE51，不含 `fork`/`exec`/MMU/动态加载），用于 C 服务与遗留代码；硬实时域仍然无 POSIX、无堆。见 [ADR-0020](05-design-decisions.md#adr-0020--posix-兼容分区)。
- ❌ **不做虚拟内存**。无 MMU 假设，只有 MPU。地址空间平坦，任务间共享同一地址空间。
- ❌ **不做动态加载的用户程序**。任务在编译期静态链接进镜像。这可避免 Tock 式"进程加载器 + 每进程 MPU 重编程"带来的开销与攻击面（Hubris 明确"never will"支持动态加载，其可靠性收益已验证）。
- ❌ **不做 SMP**。首版单核。多核 MCU（如 ESP32）以 AMP 方式各自跑一个 EchoOS 实例。
- ❌ **不做通用文件系统**。只做面向 flash 的日志结构文件系统（LittleFS 风格），针对掉电一致性。
- ❌ **不做通用 TCP/IP 协议栈**。机器人场景需要的是**实时现场总线**（EtherCAT / CAN-FD），不是互联网协议。TCP/IP 仅在需要与上位机通信时有价值，且可用更简单的方案替代。
- ⚠️ **但现场总线是主干，不是可选项**。原"网络推迟到 M9+"的决策**已被推翻**——没有总线，EchoOS 只能控制单个关节，那是电机控制器而非机器人操作系统。见 [02 §2.9](02-embodied-ai-robot-profile.md#29-现场总线为什么它是关键路径-阶段二)。
- ❌ **不做大脑层（AI 推理 / SLAM / 任务规划）**。那是 Linux + ROS 2 + AI 框架的职责。EchoOS 只提供与之对接的有界延迟接口（`echo-bridge`）。
- ❌ **不做 C 语言 ABI 兼容的完整 POSIX 层**。C 互操作限于 `extern "C"` 边界；**可选的 PSE51 子集**见 [ADR-0020](05-design-decisions.md#adr-0020--posix-兼容分区)（v1 才实现，且不在安全 case 内）。

## 1.4 竞品对标

| 项目 | 形态 | 调度 | 隔离手段 | 中断延迟* | 强项 | 短板 |
| --- | --- | --- | --- | --- | --- | --- |
| **FreeRTOS** | 宏内核 RTOS | 优先级抢占 + RR | 无（可选 MPU port） | 低 | 生态最大、认证案例多、可移植性极强 | C 语言内存安全无保障；API 一致性差 |
| **Zephyr** | 宏内核 RTOS | 优先级抢占 + RR + EDF | MPU/MMU 可选 | 低 | 子系统最全、Kconfig/devicetree 成熟 | 构建系统复杂、学习曲线陡、Rust 支持是二等公民 |
| **RT-Thread** | 宏内核 RTOS | 优先级抢占 + RR | 可选 | 低 | 组件丰富、中文资料多 | 同上；组件耦合较紧 |
| **Tock** | 微内核 | 优先级抢占 | MPU 每进程 | ~15.6 µs | 动态多应用、Rust 类型隔离 capsule | MPU 重编程开销大；延迟显著高于其它方案 |
| **Hubris** | 宏内核（静态任务） | 优先级抢占 | MPU 每任务 | 低 | 极可靠的静态配置、无动态加载 | 只支持部分 STM32；生态封闭 |
| **RTIC** | 框架（非 OS） | 中断驱动 + SRP | 类型系统（编译期） | ~4 µs | 零开销、延迟最低、编译期数据竞争检查 | **不是 OS**：无堆、无文件系统、无网络、无动态任务、所有任务共享单栈 |
| **Embassy** | async 框架 | 协作式执行器 | 类型系统 | ~10 µs | async 人体工学好、HAL 覆盖广 | **非抢占**：无优先级抢占语义，硬实时保证弱 |

\* 延迟数据来自 Cortex-M4 平台的公开对比研究（RustIEC / MDPI *Sensors* 2024），仅作量级参考，非精确基准。

### 对标结论

1. **RTIC / Embassy 不是 RTOS，是并发框架。** 它们解决了"如何安全地并发"，但没解决"如何管理资源与提供完整系统服务"。EchoOS 要在**保留它们的实时性水平**的同时，补齐子系统。
2. **Tock 的教训**：微内核 + 动态进程在 MCU 上的延迟代价是可见的（MPU 配置占主导）。除非隔离需求压倒一切，否则不该走这条路。
3. **Hubris 的启示**：静态配置 + 无动态加载 = 可靠性红利。Oxide 把这个当作特性而非限制，EchoOS 采纳同样的取舍。
4. **FreeRTOS/Zephyr 的教训**：C 语言的隔离只能靠 MPU 运行时检查，且 API 层没有编译期保证。Rust 的价值恰恰在于**把一部分隔离从运行时移到编译期**。

## 1.5 EchoOS 的差异化定位

**近期（阶段一）：FreeRTOS 的内核模型 + Rust 的编译期安全 + 面向实时控制的抖动保证。**

具体说，比 FreeRTOS 多做的三件事：

1. **零抖动静态调度**——循环执行体，编译期确定的调度表（FreeRTOS 只有 tick 驱动的抢占式）
2. **抖动可量化**——`echo-bench` 报告分布（P50/P99/P99.9/max），不是单个最大值
3. **ISR-first 控制环**——定时器 → ADC → 控制律 → PWM 的硬件时间线，全程不切上下文

**远期（阶段三）：在非确定性的 AI 栈与必须绝对可靠的物理执行器之间，建立一道不可绕过的实时边界。**

这是具身智能机器人独有的问题：**如何让一个每月都在变的、不可信的 AI 栈，安全地驱动一个必须绝对可信的实时执行层？** RTIC/Embassy 不做机器人语义；`ros2_control` 把该逻辑放在无硬实时保证、无隔离的 Linux 应用层。**没有现成的答案。**

> ⚠️ **但这项差异化建立在阶段一的确定性底座之上**——底层的抖动不受控时，任何安全包络的计算都是流沙上的建筑（[ADR-0019](05-design-decisions.md#adr-0019--分阶段交付实时控制优先)）。**先把实时控制做扎实，再谈 AI 边界。**

三条设计主线：

### 主线一：隔离从运行时前移到编译期

- 任务、优先级、栈、资源、设备在**编译期**确定（`static` + 宏 + const 泛型），运行时不做发现与分配。
- Rust 类型系统负责：数据竞争（`Send`/`Sync`）、所有权转移（IPC 消息）、资源生命周期（borrow checker）。
- 功能安全标准要求"自由度内失效"（Freedom From Interference），编译期静态配置天然满足多数条款。**在机器人场景下这一点尤其关键**——AI 域的失效绝不能传播到安全域（[ADR-0017](05-design-decisions.md#adr-0017--ai-命令是建议安全层是不可绕过的仲裁者)）。
- MPU 退居第二道防线，用于捕捉"编译期保证被 unsafe 绕过"的情形。**这直接消除了 Tock 的 MPU 热路径开销**。

### 主线二：实时性作为第一公民，且持续回归

- 内核临界区长度是**审查项**，不是事后优化项。每个 PR 都跑延迟基准。
- 默认使用优先级继承协议（PIP），杜绝无界优先级反转。
- Tickless 设计：空闲时关 tick，降低无谓中断与功耗。
- 中断上半部只做最小工作，重活用 PendSV/软中断延迟到任务上下文。

### 主线三：可测试性驱动架构

- 内核逻辑泛型化 over `Arch` trait → **内核可以在 x86 host 上单元测试**，用 `echo-arch-mock` 模拟中断与上下文切换。
- 这意味着调度器、同步原语、IPC 的逻辑正确性可以用 `cargo test` + Miri 验证，而不是只能靠上板调试。
- 这是 Rust 相对 C 的**结构性优势**，也是最值得投入的架构决策。

## 1.6 目标应用场景

**唯一目标场景：具身智能机器人。**

具体包括：

1. **人形机器人** —— 协调层 + 13–41 个关节节点，EtherCAT 同步
2. **四足机器人** —— 12–16 个关节，强平衡控制环
3. **协作机械臂** —— 6–7 个关节 + 力控，人机共处
4. **移动机器人 / AMR** —— 底盘 + 机械臂复合系统

**EchoOS 的边界**：

| 层 | 是否属于 EchoOS | 说明 |
| --- | --- | --- |
| 大脑（AI 推理、SLAM、规划） | ❌ **不属于** | Linux + ROS 2 + AI 框架。EchoOS 只提供与之对接的**有界延迟接口** |
| 小脑（协调、步态、安全包络） | ✅ **主要战场** | Cortex-M7 / Cortex-R |
| 脊髓（关节电流环、编码器） | ✅ **主要战场** | Cortex-M7 / G4 / 专用驱动芯片 |

**明确不瞄准**：通用计算、办公/音视频/服务器、富操作系统替代、需要 MMU 隔离的多租户场景、工业 PLC、汽车 ECU（这些场景的设计权衡与机器人不同——见 [02 §2.6](02-embodied-ai-robot-profile.md#26-与工业控制--汽车电子的关键差异)）。

## 1.7 依赖边界：L1 完全自研

**已决定**：EchoOS 采用 **L1（完全裸写）** 策略——**不引入任何第三方 Rust crate**，所有进入镜像的 Rust 代码均为自研。详见 [ADR-0014](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研)。

> ⚠️ **唯一例外（2026-11-10）**：可选的 POSIX 兼容分区允许链接 vendored **picolibc**（BSD-3-Clause，固定版本、随库审计），仅用于 C 服务；**硬实时域不得链接**。见 [ADR-0020](05-design-decisions.md#adr-0020--posix-兼容分区)。

### 边界定义

| 类别 | 是否允许 | 说明 |
| --- | --- | --- |
| 进入镜像的 Rust 代码 | ✅ **仅限自研** | workspace 内的 crate |
| `core` crate | ✅ 允许 | Rust 语言的一部分（`no_std` 子集），不是第三方依赖 |
| `compiler_builtins` | ✅ 允许 | 由 `rustc` 隐式链接，属于编译器运行时 |
| 编译工具链 | ✅ 允许 | `rustc` / `cargo` / `rust-lld` / `rust-objcopy`（host 侧工具，不进镜像） |
| host 侧构建/测试工具 | ✅ 允许 | QEMU、`cargo-deny`、`cargo-geiger`、自研 SVD 生成器 |
| **第三方 Rust crate** | ❌ **禁止** | 任何出现在 `[dependencies]` 中的外部 crate |
| `picolibc`（C 运行时） | ⚠️ **仅 POSIX 域** | [ADR-0020](05-design-decisions.md#adr-0020--posix-兼容分区) 的受控例外；硬实时域禁止 |

### 必须自研的关键组件

按工作量从小到大：

| 组件 | 原本可复用 | 自研工作量 | 说明 |
| --- | --- | --- | --- |
| 原子操作抽象 | `portable-atomic` | S | M3+ 有原生 CAS；M0/M0+ 需临界区模拟 |
| 寄存器访问封装 | `vcell` | S | `UnsafeCell` + 读写权限标记 |
| Cortex-M 寄存器定义 | `cortex-m` | **XL** | NVIC/SCB/SysTick/MPU/DWT/ITM 等，**用 SVD 代码生成规避**（见下） |
| 芯片外设寄存器定义 | `stm32f4xx-hal` PAC | **XL** | 每个芯片数千个位域，**必须代码生成** |
| HAL trait 体系 | `embedded-hal` | M | 自研 trait，但保持概念对齐 |
| 无堆容器 | `heapless` | M | `Vec`/`String`/`Deque` 的固定容量版本 |
| 日志/trace | `defmt` | M | 自研符号表 + host 侧解码 |
| 现场总线（CAN-FD） | 无 | **L** | 自研可行，见 [02 §2.9](02-embodied-ai-robot-profile.md#29-现场总线为什么它是关键路径-阶段二) |
| EtherCAT 从站 | 商业协议栈 | **XL+（2–4 年）** | ❌ **与 L1 正面冲突** → [Q8](09-risks-and-open-questions.md#q8--现场总线选型--最高优先级) |

### 使 L1 可落地的关键手段：SVD 代码生成

**L1 完全自研 ≠ 手写寄存器定义。** 手写数千个位域是纯负债：错误静默、无法审查、随芯片型号组合爆炸。

**对策**：自研 `svdgen`——一个跑在 host 上的代码生成器，把芯片厂商发布的 **CMSIS-SVD（XML）** 转换为 Rust 寄存器访问代码。

```
厂商 SVD 文件 (XML)  ──►  svdgen (自研, host 工具)  ──►  生成的 Rust 代码
   stm32f401.svd                                             echo-stm32f4-regs/src/*.rs
   （公开标准格式）                                            ├─ 外设结构体
                                                              ├─ 寄存器（含位域访问器）
                                                              └─ 中断号枚举
```

**为什么这仍然是"从零开发"**：

1. `svdgen` 是**我们自己的代码**，不是外部依赖。
2. 生成的代码检查进版本库，可审计、可 diff、可手工修正。
3. 产物**零外部 crate 依赖**（生成器自己输出 `UnsafeCell` 封装，不用 `vcell`）。
4. SVD 是厂商发布的**公开硬件描述标准**（ARM CMSIS 规范），不是软件依赖——等同于一页芯片参考手册。

**代价对比**：

| 方式 | 工作量 | 错误率 | 芯片适配成本 |
| --- | --- | --- | --- |
| 手写全部寄存器 | 数万行，数月 | 高（静默） | 每颗芯片重来 |
| **SVD 代码生成** | **生成器约 2000 行，数周** | 低（生成器测一次，全芯片受益） | **换芯片只换 SVD** |

**这是整个 L1 决策能否落地的分水岭。** 若跳过 `svdgen` 改用手写，M1 的周期将从数周变成数月，且后续每支持一颗新芯片都要重复付出。

### 需要接受的现实

- **M1/M2 的周期显著长于 L2 方案**（多出寄存器定义与基础抽象层的工作）。
- **放弃生态系统红利**：第三方 `embedded-hal` 驱动无法直接使用，需要移植。这是长期成本，不是一次性成本。
- **总线能力是最大不确定性**：EtherCAT 与 L1 正面冲突（见 [02 §2.9](02-embodied-ai-robot-profile.md#29-现场总线为什么它是关键路径-阶段二)）。这是 L1 策略下**唯一没有捷径**的部分，也是当前的最高优先级问题。
- **换取**：完全可控、零供应链风险、零许可证兼容问题、可完整审计每一个字节的镜像、以及教学/研究价值——每行代码都是自己的，出问题一定能查到根因。
