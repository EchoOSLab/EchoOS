# 02 · 具身智能机器人场景分析

> 本文是 EchoOS 的**需求基线**。目标场景已明确为**具身智能机器人**——不是工业控制、不是汽车 ECU、不是通用嵌入式。这一节重新推导设计需求，并指出 [01](01-vision-and-scope.md) 中哪些结论仍然成立、哪些必须改变。

## 2.1 场景重定位带来的根本变化

从"通用嵌入式 RTOS"到"具身智能机器人 RTOS"，变化不只是"性能要求更高"，而是**问题的形状变了**：

| 维度 | 通用嵌入式 RTOS | 具身智能机器人 RTOS |
| --- | --- | --- |
| 系统形态 | 单节点、自包含 | **多节点、强耦合**：大脑 + 协调 + N 个关节 |
| 关键指标 | 中断延迟、吞吐 | **抖动（jitter）与节点间同步**，而非单纯延迟 |
| 负载特征 | 混合负载、事件驱动 | **严格周期性、多速率**：电流环/速度环/位置环/规划器/AI |
| 最难的边界 | 中断 ↔ 任务 | **非确定性 AI ↔ 硬实时执行器** |
| 数据流 | 外设 ↔ 任务 | 传感器 → 融合 → 控制 → 总线 → 执行器，**闭环有硬截止时间** |
| 失效后果 | 系统不可用 | **物理伤害**（机器人是人机共处的物理系统） |
| 总线 | 可选、辅助 | **主干**：EtherCAT / CAN-FD，是实时链路的一部分 |
| 内存系统 | 简单（无 cache 或无 D-cache） | **Cortex-M7 带 D-Cache + DMA**，一致性成为核心问题 |

**结论：现有方案中"通用 RTOS"的框架仍然成立，但三个新的核心问题必须补充设计**（见 §2.6）。同时，[01 §1.3](01-vision-and-scope.md#13-明确非目标non-goals) 中"首版不做网络协议栈"的决策**与机器人场景直接冲突**（见 §2.7）。

## 2.2 架构参照：FreeRTOS + 实时控制增强

EchoOS 的架构**仿照 FreeRTOS**：一个精简的宏内核，配上清晰的移植层与可裁剪的可选组件。Rust 负责把 FreeRTOS 里靠约定维持的部分变成编译期保证；实时控制增强则是 EchoOS 相对 FreeRTOS 的价值增量。

### 与 FreeRTOS 的结构对照

| FreeRTOS | EchoOS | 说明 |
| --- | --- | --- |
| `tasks.c` | `echo-sched` | 调度器、任务、优先级 |
| `queue.c` | `echo-ipc` | 队列、通道 |
| `semphr.c` / `event_groups.c` | `echo-sync` | 信号量、互斥量、事件组 |
| `timers.c` | `echo-time` | 软件定时器、时基 |
| `heap_1..5.c` | `echo-mm` | 内存管理（静态优先 + 确定性池） |
| `portable/[compiler]/[arch]/` | `echo-arch-*` | 移植层（唯一的汇编所在） |
| `FreeRTOSConfig.h` | `echo-config` | 编译期配置 |
| `taskENTER_CRITICAL` | `echo-critical` | 临界区 |
| `FreeRTOS+TCP` / `+FAT` / `+CLI` | `crates/services/*` | 可选组件，逐个独立 |
| `croutine.c`（协程，少用） | — | 不实现 |

**结论：分层与模块划分基本一一对应。** 这带来一个实际好处——FreeRTOS 的文档、教程、设计思路都可以直接参考，学习成本低。

### 相对 FreeRTOS 的增强

这些是 EchoOS 的**价值增量**，也是"为什么要重写一个 RTOS"的答案：

| FreeRTOS 的做法 | 问题 | EchoOS 的增强 |
| --- | --- | --- |
| tick 驱动调度，典型 1 kHz | 周期任务抖动达一个 tick（1 ms）——对控制环不可接受 | **硬件定时器直接触发** + tickless（[ADR-0016](05-design-decisions.md#adr-0016--循环执行体作为一等调度模式)） |
| 无静态调度能力 | 抖动不可消除 | **循环执行体**：编译期确定的调度表，零抖动 |
| 抖动无度量 | 只能测最大值，看不到分布 | `echo-bench` **报告 P50/P99/P99.9/max** |
| 临界区默认关全部中断（`PRIMASK`） | 高优先级中断被连带延迟 | **`BASEPRI`**：只屏蔽会访问内核数据的中断（[ADR-0006](05-design-decisions.md#adr-0006--临界区使用-basepri-而非-primask)） |
| C 语言，无类型安全 | ISR 里误调阻塞 API 只能运行时断言 | **类型区分** `TaskContext`/`IsrContext`，编译期失败 |
| 动态分配为主（`heap_4` 有碎片） | 分配时间不可预测 | **默认无堆**，内存池 `O(1)` 无碎片（[ADR-0008](05-design-decisions.md#adr-0008--默认无堆需要时提供确定性分配器)） |
| 配置宏 `#define`，错误靠人眼 | 配置错误运行期才暴露 | `const` + **`const_assert!`** 编译期校验（[ADR-0007](05-design-decisions.md#adr-0007--编译期静态配置const--cfg不用运行时配置)） |
| 依赖 C 约定维持隔离 | 越界/数据竞争靠 MPU 事后捕获 | **Rust 类型系统前移隔离**，MPU 退为纵深防御（[ADR-0003](05-design-decisions.md#adr-0003--组件化宏内核而非微内核)） |

> **一句话**：EchoOS ≈ FreeRTOS 的内核模型 + Rust 的编译期安全 + 面向实时控制的抖动保证。

### 不照搬 FreeRTOS 的地方

| FreeRTOS | EchoOS | 理由 |
| --- | --- | --- |
| 单一巨型源码树 | 多 crate workspace | Rust 生态惯例；依赖边界由编译器强制（[ADR-0001](05-design-decisions.md#adr-0001--采用-cargo-workspace-多-crate-布局)） |
| 移植层反向调用内核（`extern` 符号） | 内核泛型化 over `Arch` trait | **内核逻辑可在 host 上单元测试**（[ADR-0002](05-design-decisions.md#adr-0002--内核泛型化-over-arch-trait)） |
| 运行时动态创建任务为主 | 编译期静态注册 | 静态配置是可靠性与可分析性的基础 |
| `configUSE_*` 大量布尔宏 | **const + 扁平 feature**，避免 2^N 组合 | 宏组合爆炸无法在 CI 中全测（[ADR-0007](05-design-decisions.md#adr-0007--编译期静态配置const--cfg不用运行时配置)） |

## 2.3 分阶段交付策略 ★

**这是本方案最重要的范围约束。**

具身智能机器人的完整愿景包含 AI 接入，但那是一个**依赖关系极强的上层**。分三个阶段交付，每个阶段独立可用：

```
阶段一 · 实时控制内核          阶段二 · 机器人运动控制        阶段三 · AI 接入
─────────────────────        ─────────────────────        ─────────────────
★ 当前专注                    （阶段一完成后）              （阶段二完成后）

调度器 / 同步 / IPC            现场总线（CAN-FD）            echo-bridge
内存 / 时间 / 驱动             多关节协调                     echo-safety
循环执行体（零抖动）            运动学 / 轨迹插值               AI 命令仲裁
ISR-first 控制环                双节点闭环（V2 切片）          与 AI 栈联调
单关节闭环（V1 切片）
                            产出：多关节机器人            产出：AI 能安全驱动
产出：能跑电机、能量化         能协调运动                    机器人
      抖动的 RTOS
```

### 为什么必须先做阶段一

这不只是"先易后难"的排序，而是**逻辑上的依赖**：

1. **AI 安全层的意义完全建立在确定性底座之上。** `echo-safety` 要保证"AI 命令不会导致物理危险"，这个保证的前提是**执行层本身的行为是可预测的**。如果底层的抖动不受控、截止时间会漂移，那么任何安全包络的计算都是建立在流沙上的。
2. **阶段一本身就是可交付的成果。** 一个能在 STM32H7 上跑电机控制、抖动可量化、零依赖的 Rust RTOS——**它不需要 AI 就有价值**。这直接缓解了 [风险 P1（范围过大）](09-risks-and-open-questions.md#92-项目风险)。
3. **AI 侧的技术栈每几个月就变一次。** 把它作为第一优先级，会让整个项目的接口反复重写（[风险 T24](09-risks-and-open-questions.md#910-具身智能机器人场景引入的新风险)）。先做稳定的底层，等 AI 侧成熟了再接。

### 各阶段的详细范围

| | 阶段一 · 实时控制内核 | 阶段二 · 机器人运动控制 | 阶段三 · AI 接入 |
| --- | --- | --- | --- |
| **里程碑** | [M0–M6](08-roadmap.md#82-里程碑总览) + [M7 实时控制增强](08-roadmap.md) | M8 现场总线 + M9 多关节协调 | M10 AI 桥接与安全仲裁 |
| **crate** | `core/*` `arch/*` `regs/*` `kernel/*` `api/*` `services/driver,hal` | `echo-fieldbus` `echo-can` `echo-motion` `echo-sensor` | `echo-bridge` `echo-safety` |
| **关键验证** | **V1 单关节切片**：示波器测抖动分布 | **V2 双节点切片**：总线同步精度 | 故障注入：AI 崩溃/超时/越限 |
| **产出** | 能跑 BLDC 电机、抖动可量化、零依赖的 RTOS | 多关节机器人能协调运动 | AI 能安全驱动机器人 |
| **本阶段不做什么** | 不做总线、不做多关节、不做 AI 接口 | 不做 AI 仲裁、不做通用网络 | — |

### 对现有文档的影响

**阶段一之外的设计仍然保留在文档中**，但明确标注为后续阶段，避免它们污染当前的设计决策：

- [`echo-bridge` / `echo-safety`](06-subsystems.md#68-机器人子系统-机器人场景新增) —— **阶段三**，当前只做接口预留，不实现
- [ADR-0017（AI 命令是建议）](05-design-decisions.md#adr-0017--ai-命令是建议安全层是不可绕过的仲裁者) —— **阶段三**，但它是**架构不变式**，现在就要在依赖规则中固化（`bridge` 不得被 `safety` 以下依赖）
- [现场总线](02-embodied-ai-robot-profile.md#29-现场总线为什么它是关键路径-阶段二) —— **阶段二**，当前只需保证 `echo-fieldbus` 的抽象位置预留
- [循环执行体](06-subsystems.md#61-调度器echo-sched) / [缓存与 TCM](03-architecture.md#357-内存分层与缓存-机器人场景新增) —— **阶段一**，这两个是当前的设计内容

## 2.4 具身智能机器人的系统架构

### 三层算力模型

```
┌───────────────────────────────────────────────────────────────┐
│ 大脑 · AI 推理层                                                │
│   VLA 模型 / 任务规划 / SLAM / 视觉                             │
│   硬件：Jetson Orin (A78AE + GPU) / x86 + RTX / 国产 AI 芯片     │
│   软件：Linux + ROS 2 + PyTorch                                 │
│   频率：1–50 Hz        确定性：无（尽力而为，有长尾延迟）          │
└───────────────────────────┬───────────────────────────────────┘
                            │  以太网 / 共享内存 / 串口
                            │  ← ★ 不可信边界：命令必须被校验
┌───────────────────────────▼───────────────────────────────────┐
│ 小脑 · 协调层（EchoOS 的主要战场）                               │
│   全身运动学 / 步态 / 平衡控制 / 轨迹插值 / 安全包络              │
│   硬件：STM32H7 (Cortex-M7 @480MHz) / Cortex-R52 / Jetson 安全岛 │
│   频率：100–1000 Hz    确定性：硬实时                            │
└───────────────────────────┬───────────────────────────────────┘
                            │  EtherCAT / CAN-FD
┌───────────────────────────▼───────────────────────────────────┐
│ 脊髓 · 关节执行层（EchoOS 的第二个战场）                          │
│   电流环 FOC / 编码器读取 / 力矩控制 / 制动器                     │
│   硬件：STM32G4/H7 / TI C2000 / 专用电机驱动芯片                  │
│   频率：10–40 kHz      确定性：硬实时（最紧）                     │
└───────────────────────────────────────────────────────────────┘
                            │  PWM
                       电机 + 减速器 + 关节
```

**EchoOS 的定位**：运行在**小脑层与脊髓层**。大脑层是 Linux + AI 框架，**不在 EchoOS 范围内**——这是刻意的边界。

> 一个值得注意的选项：Jetson Orin 内部有 **Cortex-R5F 安全岛**（锁步双核）。若能支持它，EchoOS 可以与 AI 栈运行在同一 SoC 上，通过共享内存而非以太网通信——延迟从毫秒级降到微秒级。这是**战略级的机会**，但需要第三个架构移植（Cortex-R）。

### 通信拓扑

典型人形/四足机器人：**1 个协调节点 + 12–40 个关节节点**，EtherCAT 菊花链拓扑。

```
协调节点 ──► 关节1 ──► 关节2 ──► ... ──► 关节N ──► 回到协调节点
   (主站)      (从站)                                  （环网，冗余）
```

**全部节点在同一总线上，由同一个分布式时钟同步。** 协调节点的周期与总线周期对齐——这意味着 **EchoOS 的时基必须能与外部总线时钟同步**，而不只是自己的 SysTick。

## 2.5 实时需求的量化

### 控制环分层与频率

| 环 | 典型频率 | 周期 | 抖动预算 | 运行位置 |
| --- | --- | --- | --- | --- |
| 电流环（FOC） | 10–40 kHz | 25–100 µs | < 1 µs | 关节节点，常在定时器 ISR 内 |
| 速度环 | 1–4 kHz | 250 µs–1 ms | < 5 µs | 关节节点 |
| 位置环 | 100–1000 Hz | 1–10 ms | < 20 µs | 关节节点 / 协调节点 |
| 平衡/步态 | 500 Hz–1 kHz | 1–2 ms | < 20 µs | 协调节点 |
| 轨迹插值 | 100–500 Hz | 2–10 ms | < 100 µs | 协调节点 |
| AI 命令 | 1–50 Hz | 20 ms–1 s | 无要求 | 大脑层 |

**关键观察**：**电流环运行在 ISR 里，不在任务里。** 这是机器人控制的通行做法——25 µs 的周期里没有上下文切换的预算。RTOS 的任务调度服务于 1 kHz 及以下的层次。

> 这修正了 [03 §3.2](03-architecture.md#32-内核形态组件化宏内核) 中"所有实时工作都在任务里"的隐含假设。EchoOS 必须支持**"ISR 优先"的控制模式**：定时器中断 → 直接执行控制律 → 输出 PWM，全过程不切上下文。

### 抖动比延迟更重要

工业与机器人领域的一个常见误判：追求"更低的延迟"。实际上对闭环控制：

- 一个**稳定地**晚 50 µs 执行的控制环，控制器的相位裕度计算里已经包含这个常数延迟 → **无害**
- 一个**偶尔**晚 50 µs 的控制环 → 引入随频率变化的相位扰动 → **激起振荡**

因此 EchoOS 的目标函数应修正为：

| 指标 | 原目标（[01 §1.2](01-vision-and-scope.md#12-设计目标)） | 修正后 |
| --- | --- | --- |
| 中断延迟 P99 | < 1 µs | < 1 µs（保持） |
| **中断延迟抖动（P99 − P50）** | 未定义 | **< 200 ns** ← 新增，且**优先级高于绝对值** |
| **上下文切换抖动** | 未定义 | **< 300 ns** ← 新增 |
| 周期任务触发抖动 | 未定义 | **< 1 µs**（1 kHz 环） |
| 上下文切换（平均） | < 2 µs | < 1.5 µs（收紧） |

**度量方式的改变**：`echo-bench` 必须报告**分布**（P50/P99/P99.9/max），而不只是最大值。一个偶发的 10 µs 尖峰比稳定的 2 µs 危险得多。

### 多速率确定性

机器人的任务集是**严格周期的多速率集合**：

```
时间轴（1 ms 主周期）
0        125µs    250µs    375µs    500µs    625µs    750µs    875µs   1ms
├─────────┼─────────┼─────────┼─────────┼─────────┼─────────┼─────────┼─────────┤
│ 速度环(1kHz)  │    │         │         │ 速度环  │         │         │         │
│      IMU 采样(8kHz，硬件触发，独立于本时间轴)                    │
│                     │ 位置环(500Hz)    │                   │ 位置环            │
│                                                       │ 平衡控制(500Hz)      │
└───────────────────────────────────────────────────────────────────────────┘
      AI 命令到达（异步，1–50 Hz，无固定相位）
```

**这对调度器提出了新要求**：

1. **零抖动的周期触发**。tick 驱动的调度（每 tick 唤醒任务）抖动为一个 tick 周期（1 kHz tick → 1 ms 抖动）——**完全不可接受**。必须用**硬件定时器直接触发**，或使用高分辨率定时器与专用比较通道。
2. **相位关系可控**。位置环必须在速度环之后固定偏移执行，不能随机漂移。
3. **超时/超限可观测**。截止时间错过必须被检测、记录、并触发安全响应，而不是静默延迟。

详见 §2.6.2。

### 节点间同步

| 方案 | 同步精度 | 说明 |
| --- | --- | --- |
| EtherCAT 分布式时钟（DC） | **< 100 ns** | 行业标准，人形机器人主流 |
| CAN-FD + 自定义同步帧 | ~10–100 µs | 成本低，精度差一个数量级 |
| PTP (IEEE 1588) | < 1 µs | 需要硬件时间戳 |

**含义**：EchoOS 的时基必须**可被外部时钟驯服**（disciplined）——本地计数器与总线时钟之间需要一个可调偏移/速率的同步层。这不只是"加个协议"，它影响 `echo-time` 的核心设计。

### 传感器采样与控制的同步

最苛刻的确定性要求不在软件，而在**采样时刻**：

```
定时器 ──┬──► 触发 ADC 采样（硬件，零软件抖动）
         ├──► 触发 PWM 更新（硬件）
         └──► 触发 CPU 中断 → 执行控制律
```

三者由**同一个硬件定时器事件**触发，软件抖动不影响采样时刻。这是 STM32 的定时器联动（TRGO → ADC 外部触发 → DMA → PWM 更新）能力。

**EchoOS 的驱动模型必须原生支持这种"硬件时间线"**，而不是把一切都抽象成"任务里读传感器"。详见 §2.6.3。

## 2.6 与工业控制 / 汽车电子的关键差异

原方案（[01](01-vision-and-scope.md)）把工业控制与汽车 ECU 作为目标场景。机器人场景的差异：

| 维度 | 工业控制 | 汽车 ECU | **具身智能机器人** |
| --- | --- | --- | --- |
| 节点数 | 少（1–5） | 多（10–100），但功能独立 | **中（13–41），但强耦合、需同步** |
| 同步要求 | 宽松 | 中等（CAN） | **极严（< 100 ns，EtherCAT DC）** |
| 控制环 | 单一（1 kHz 左右） | 多速率 | **深度多速率（40 kHz 到 1 Hz）** |
| 上层智能 | 无 / 简单 | 规则式 | **非确定性 AI（VLA 大模型）** ← 全新 |
| 失效后果 | 停机、损失 | 人身安全 | **人身安全 + 物理接触** |
| 标准 | IEC 61131 | ISO 26262 | ISO 10218 / ISO/TS 15066 + 功能安全 |
| 软件栈 | 封闭、固定 | AUTOSAR 主导 | **开放、快速演进（AI 侧每月都在变）** |

**最重要的差异是最后两行**：机器人是**人机共处的物理系统**，且其上层是一个**每月都在变化的 AI 栈**。

这产生了一个工业与汽车都不存在的问题：**如何让一个快速演进的、不可信的 AI 栈，安全地驱动一个必须绝对可信的实时执行层？**

## 2.8 三个新的核心设计问题

> **阶段归属**：§2.8.2（多速率确定性）与 §2.8.3（缓存与 TCM）属**阶段一**，是当前的设计内容；§2.8.1（AI 边界）属**阶段三**，当前只固化架构不变式、不实现。

### 2.8.1 AI 与硬实时的边界：安全包络与命令仲裁 ★ 【阶段三】

> ⏩ **本小节属于阶段三（AI 接入），当前不实现。** 保留在此是因为它确立了架构不变式（AI 命令是建议、安全层不可绕过），该不变式现在就要在依赖规则中固化。参见 [§2.3 分阶段交付策略](#23-分阶段交付策略-)。

**这是具身智能 RTOS 区别于一切现有 RTOS 的核心问题，也是最值得投入的设计。**

**问题**：AI 栈（Linux + 大模型）会产生：
- **不安全的命令**（超出关节限位、速度过快、轨迹不连续）
- **迟到的命令**（长尾延迟、GC 暂停、模型推理超时）
- **不存在的命令**（进程崩溃、通信中断）
- **格式错误的命令**（版本不匹配、内存损坏）

而执行器是物理的。**任何一条都必须被拦截。**

**设计：三层防护**

```
                    AI 栈（不可信，尽力而为）
                         │ 命令：目标关节轨迹 @ 1–50 Hz
                         ▼
┌──────────────────────────────────────────────────────────────┐
│ 第 1 层 · echo-bridge —— 传输边界                              │
│  · 固定布局的共享内存环（无序列化、无分配、O(1)）                │
│  · 序号 + 时间戳 + CRC：检测丢失、错序、损坏                    │
│  · 版本协商：AI 栈与 RTOS 的接口版本必须匹配，否则拒绝           │
│  · 无锁：RTOS 侧读，AI 侧写，永不阻塞                           │
│  ⚠️ 此层只保证"传过来的东西是完好的"，不保证"内容是安全的"        │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ 第 2 层 · echo-safety —— 语义边界（不可绕过）                   │
│  · 新鲜度：命令超时 → 拒绝，进入受控减速                        │
│  · 关节限位：位置 / 速度 / 加速度 / 加加速度 / 力矩              │
│  · 工作空间：末端执行器边界、自碰撞、奇异位形                    │
│  · 速率限制：命令变化率（防止"瞬移"）                            │
│  · 状态机：INIT → READY → ACTIVE → DAMPING → FAULT → ESTOP     │
│  · 任何一项失败 → 拒绝命令 + 记录 + 按严重度降级                 │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ 第 3 层 · echo-motion —— 时间边界                              │
│  · 把 1–50 Hz 的不规则航点插值到 1–10 kHz 的规整设定点           │
│  · 加加速度（jerk）限制，保证 C² 连续，避免机械冲击              │
│  · 多关节共享同一时间基准（与总线周期对齐）                      │
│  · 插值保证有界延迟：即使新命令迟到，也已有一条安全轨迹在跑       │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
                    控制环任务 / ISR（硬实时）
```

**关键设计原则**：

> **AI 的输出是"建议"（proposal），不是"命令"（command）。RTOS 侧的安全层是不可绕过的仲裁者，且它永远有一条"当前安全轨迹"在跑——AI 失联只会让它平滑减速，不会让它失控。**

这一原则同时满足：
- 功能安全的"自由度内失效"（Freedom From Interference）
- 机器人安全标准的"安全状态"要求（ISO 10218 / ISO/TS 15066）
- 工程上的"优雅降级"（AI 崩了机器人不会摔）

**为什么现有 RTOS 不做这个**：FreeRTOS/Zephyr 是通用内核，它们抽象的是"任务与资源"，不是"机器人动作"。而 `ros2_control` 把这个逻辑放在 Linux 应用层——**没有硬实时保证，且 AI 栈与安全层在同一地址空间，隔离不成立**。

**这是 EchoOS 最清晰的差异化点。**

### 2.8.2 多速率确定性：循环执行体 vs 优先级抢占 【阶段一】

**问题**：优先级抢占调度在通用 RTOS 里是正确答案，但它的抖动特性不适合多速率控制：

| 特性 | 优先级抢占 | 静态循环执行体 |
| --- | --- | --- |
| 抖动来源 | 抢占时机取决于事件到达 | **零**——调度表在编译期确定 |
| 可分析性 | 需响应时间分析（RTA），复杂 | **直接读出**——每个槽位固定 |
| 突发负载 | 自适应，灵活 | 无弹性，超限即错 |
| 适用 | 事件驱动、混合负载 | **严格周期、多速率控制** |

**决定：EchoOS 同时提供两者，且让它们共存。**

```
主周期（由硬件定时器触发，如 1 ms）
┌────────┬────────┬────────┬────────┬────────┬────────┐
│ 槽 0   │ 槽 1   │ 槽 2   │ 槽 3   │ 槽 4   │ 槽 5   │
│ 速度环 │ 位置环 │ 平衡   │ 插值   │ 安全   │ 空闲   │
│ 200µs  │ 100µs  │ 200µs  │ 100µs  │ 50µs   │ 350µs  │
└────────┴────────┴────────┴────────┴────────┴────────┘
   ↑ 编译期生成的静态调度表（ADR-0007 的编译期静态配置哲学）

并行：优先级抢占任务（通信、诊断、日志、shell）
      —— 只在循环执行体的空闲槽位运行，或被显式允许抢占
```

**这恰好是 [ADR-0007](05-design-decisions.md#adr-0007--编译期静态配置const--cfg不用运行时配置) 的自然延伸**：调度表是一个编译期常量，`echo-sched` 提供 `CyclicExecutive<SCHEDULE>` 类型，其中 `SCHEDULE` 是 const 泛型参数。超限检测在编译期可通过 `const_assert!` 做部分校验。

**两种模式的边界**（重要，避免设计混乱）：

- **循环执行体域**：控制律、插值、安全校验、传感器处理 —— 严格要求周期性
- **抢占任务域**：通信、诊断、日志、shell、文件系统 —— 事件驱动，可容忍抖动
- **跨域通信**：通过 `echo-ipc` 的有界队列，非阻塞发送

### 2.8.3 缓存与 TCM：Cortex-M7 的现实 【阶段一】

原方案的示例平台是 Cortex-M3/M4（无 D-Cache）。**机器人关节控制器的主流是 STM32H7（Cortex-M7 @ 480 MHz，带 D-Cache + TCM）**。这引入了原方案完全没有覆盖的问题：

**内存分层**

```
┌─────────────────────────────────────────────────────┐
│ ITCM (64 KB)  零等待、不可缓存                         │
│   → 中断向量表、控制律代码、PendSV/SVC               │  ← 硬实时代码放这里
├─────────────────────────────────────────────────────┤
│ DTCM (128 KB) 零等待、不可缓存                         │
│   → 控制任务的栈、实时数据、DMA 缓冲区                │  ← 硬实时数据放这里
├─────────────────────────────────────────────────────┤
│ AXI SRAM / SRAM1-4 (可缓存，经 D-Cache)               │
│   → 通用数据、大缓冲区                                │
├─────────────────────────────────────────────────────┤
│ 外部 SDRAM (可缓存)                                    │
│   → 帧缓冲、大数组（非实时）                          │
└─────────────────────────────────────────────────────┘
```

**由此产生的四类新问题**：

| 问题 | 后果 | EchoOS 的对策 |
| --- | --- | --- |
| **DMA 与 D-Cache 不一致** | DMA 写入的数据被 CPU 读到旧缓存值；CPU 写的数据未回写就被 DMA 发出 | MPU 把 DMA 缓冲区标为非缓存，或提供显式的 clean/invalidate API 并强制配对使用 |
| **控制律代码不在 TCM** | 指令 Cache Miss → 抖动尖峰（几十到几百纳秒） | `#[echo::tcm]` 属性，把函数放入 ITCM 段；链接脚本支持 |
| **栈在被缓存的 RAM** | 中断入口的栈操作可能 miss | 硬实时任务的栈放在 DTCM |
| **MPU region 的 cache 属性配置错误** | 静默的数据损坏，只在特定时序下出现 | MPU 配置 API 强制显式声明 cache 属性；启动时校验 |

**这是一个必须写进 `echo-mm` 与 `echo-arch-cortex-m` 的完整设计**，原方案完全没有涉及。它也是 §2.3 抖动目标能否达成的关键——**480 MHz 的 M7 上，一次 D-Cache Miss 的代价可能超过整个上下文切换时间。**

**好消息**：Cortex-M7 的 MPU 提供了 `TEX`/`C`/`B`/`S` 位来声明内存属性，静态分区方案（[ADR-0005](05-design-decisions.md#adr-0005--单地址空间--mpu-静态分区)）可以直接扩展为"分区 + 缓存属性"的联合配置——**架构方向不需要改，只需要补充。**

## 2.9 现场总线：为什么它是关键路径 【阶段二】

**这是场景重定位后与原方案冲突最大的地方。**

[01 §1.3](01-vision-and-scope.md#13-明确非目标non-goals) 明确"首版不做网络协议栈"，网络能力被推迟到很远，且建议止步于 CAN/Modbus 类的简单链路层。**在机器人场景下这个决策不成立**：

1. **总线是实时链路的一部分**，不是附加功能。力矩命令必须**在控制周期内**送达 40 个关节，且所有关节同时生效（同步误差 < 100 ns）。
2. **没有总线，EchoOS 只能控制单个关节**——那是一个电机控制器，不是机器人操作系统。
3. **总线周期与协调节点周期强耦合**。EchoOS 的时基、调度、超限检测都与总线周期绑定。

### 候选总线与 L1 策略的冲突

| 总线 | 周期 | 同步精度 | 自研难度 | 与 L1 的关系 |
| --- | --- | --- | --- | --- |
| **CAN-FD** | 1 ms | ~50 µs | **可行**（协议简洁，约 3–6 个月） | ✅ 符合 L1 |
| **EtherCAT 从站** | 31.25–1000 µs | **< 100 ns** | ❌ **极难**：ETG 规范 2000+ 页，含 DC 时钟同步、状态机、邮箱协议、一致性测试 | ❌ **与 L1 直接冲突** |
| 自定义高速串口 | 100 µs | ~1 µs | 可行 | ✅ 符合 L1 |
| TSN / 以太网 | 1 ms | < 1 µs | 极难 | ❌ 冲突 |

**EtherCAT 是问题的核心**：它几乎是人形机器人的事实标准（高同步精度、成熟生态、专用 ESC 芯片），但**从零实现一个 EtherCAT 从站栈，本身就是 2–4 年的工程**，还要过 ETG 一致性测试。

**这暴露了 L1 策略的边界问题**：

> **从零开发一个 RTOS ≠ 从零实现别人制定的 2000 页外部协议标准。**
>
> RTOS 的核心价值在于调度、内存、同步、隔离、可移植性——这些是 EchoOS 应该从零构建的。而 EtherCAT 是一个**外部标准的实现**，与"操作系统"这一概念正交。自己实现它，不会让 EchoOS 更像一个操作系统，只会推迟它。

这不是要求推翻 [ADR-0014](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研)，而是要求**明确 L1 的适用范围**。详见 [09 §9.3 Q2 复议](09-risks-and-open-questions.md#93-待确认问题)。
