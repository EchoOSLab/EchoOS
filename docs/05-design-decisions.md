# 05 · 关键设计决策（ADR）

每条决策记录格式：**背景 → 候选方案 → 决定 → 理由 → 后果**。状态分为：已决定 / 待定 / 需重审。

---

## ADR-0001 · 采用 Cargo workspace 多 crate 布局

**状态**：已决定

**背景**：项目从零开始，需要同时服务内核、移植层、驱动、中间件、BSP、示例。这些部分的目标平台、依赖、`unsafe` 策略都不同。

**候选**：
- A. 单 crate + Cargo feature
- B. 多 crate workspace

**决定**：B。

**理由**：
1. 依赖边界由编译器强制，而非靠 review 维持。
2. `unsafe` 可以按 crate 精确授权（`deny(unsafe_code)` 与白名单并存）。
3. 增量编译收益：改动 BSP 不重编内核。
4. 可用 `xtask` 自动校验分层，让架构约束可执行。

**后果**：
- ⚠️ 必须维护 `xtask`，否则多 target 构建体验会很糟。
- ⚠️ crate 数量（当前设计约 42 个，含阶段二/三的预留）有维护成本，需要严格的命名与文档约定。

## ADR-0002 · 内核泛型化 over `Arch` trait

**状态**：已决定（**本方案中最重要的决策**）

**背景**：内核需要与体系结构交互（关中断、切上下文、读时钟、编 MPU）。这些交互如何抽象，决定了可移植性和可测试性。

**候选**：
- A. 内核 `Kernel<A: Arch>` 泛型化，arch 实现 trait
- B. 移植层反向调用内核（FreeRTOS 风格，`extern "Rust"` 符号）
- C. 运行时 `dyn Arch` 动态分发

**决定**：A 为主，B **仅**用于无法泛型化的纯汇编边界（异常入口、上下文切换）。

**理由**：
1. **可测试性是决定因素。** 方案 A 允许 `echo-arch-mock` 在 x86 host 上实现 `Arch`，从而用 `cargo test` 验证调度器、同步原语、IPC 的全部逻辑。方案 B 做不到——内核与汇编入口强耦合。
2. 单态化 = 零运行时开销。方案 C 的间接调用在 ISR 热路径上不可接受。
3. 编译期类型检查完整，错误在编译期而非链接期发现。

**后果**：
- ⚠️ 内核代码被 `<A: Arch>` 泛型参数污染。通过 `type Kernel = ...` 别名和 `echo-kernel::instance()` 单例封装缓解。
- ⚠️ 需要设计 `Arch` 的**对象安全边界**——哪些方法必须 `&self`/静态，哪些可以用 `Self::Assoc`。
- ✅ 换来的是：内核逻辑 90% 可在 host 上测试。这是整个项目的质量基石。

## ADR-0003 · 组件化宏内核，而非微内核

**状态**：已决定

**背景**：隔离强度与实时性/复杂度之间存在张力。

**候选**：微内核（Tock）、单体内核（FreeRTOS）、组件化宏内核。

**决定**：组件化宏内核——单地址空间、子系统为独立 crate、MPU 作纵深防御。

**理由**：
1. MCU 上 MPU 重编程成本与 IPC 成本相对于总预算占比过高（Tock 15.6 µs vs RTIC 4 µs）。
2. Rust 已把大量隔离移到编译期，运行时不需重复付费。
3. 单地址空间下子系统间是类型化函数调用，无序列化、无拷贝。

**后果**：
- ⚠️ 一个子系统中的 `unsafe` UB 可能影响全系统 → 由 ADR-0010 的 unsafe 策略与 Miri 缓解。
- ⚠️ 无法支持"第三方不可信代码动态加载" → 明确列为非目标。
- ✅ 延迟与吞吐显著优于微内核方案。
- ✅ 子系统仍是独立 crate，保留了将来"把某个子系统移出内核"的可能性。

## ADR-0004 · 线程模型作为调度基础，async 仅作可选适配层

**状态**：已决定（⚠️ **部分修正**——见 [ADR-0016](#adr-0016--循环执行体作为一等调度模式)）

> **修正说明（2026-09-22）**：目标场景明确为具身智能机器人后，本决策的"线程抢占是唯一调度基础"这一隐含假设被修正。机器人的多速率控制负载需要**静态循环执行体**（零抖动），因此 [ADR-0016](#adr-0016--循环执行体作为一等调度模式) 增加其为**一等调度模式**。
>
> 本 ADR 中"不用 async 做内核调度"的结论**保持不变**；新增的是循环执行体，与 async 无关。修正后的调度模型是：**循环执行体（控制域）+ 优先级抢占线程（服务域）**。

**背景**：Rust 生态中 Embassy 证明了 async 在嵌入式的可行性（延迟约 10 µs），RTIC 用中断驱动 + SRP 达到约 4 µs。EchoOS 应该用哪种？

**候选**：
- A. 线程 + 抢占调度（传统 RTOS）
- B. async 执行器 + 优先级
- C. 混合：内核线程 + 应用侧 async 适配

**决定**：A 为基础，C 作为可选的 `echo-async` crate。

**理由**：
1. **硬实时要求有界响应。** 协作式调度器在任务不 `await` 时无法抢占，无法给出上界。
2. 中断无法 `await`。"ISR 唤醒任务"的语义在阻塞模型下清晰且可分析。
3. 栈深度可静态分析（每任务独立栈 + 水位线检测）；async 的状态机大小难以人工审查。
4. async 的优势在 I/O 密集的人体工学，不在延迟——而延迟是 EchoOS 的第一目标。

**后果**：
- ⚠️ 大量并发的 I/O 等待需要更多任务与栈 → 由 `echo-mm` 的内存池与可配置栈大小缓解。
- ✅ 实时性语义清晰，可对每个任务做 WCET/栈深度分析。
- ✅ 应用仍可用 async 写业务逻辑（`echo-async` 提供 Future 适配器）。

## ADR-0005 · 单地址空间 + MPU 静态分区

**状态**：已决定

**背景**：MCU 通常无 MMU。Cortex-M 的 MPU 提供 8/16 个可编程 region。

**候选**：
- A. 不用 MPU，纯靠类型系统
- B. 每次上下文切换重编程 MPU（Tock 式）
- C. **静态分区：region 启动时固定，仅栈守卫动态更新**

**决定**：C。MPU region 在启动时一次性配置，只有"栈守卫 region"在切换任务时更新（且仅在切换到不同任务时）。

**理由**：
1. Tock 的实测表明 MPU 重编程是延迟的主要来源，不能放在热路径上。
2. 静态分区已能覆盖最主要的风险：任务栈溢出、任务越界访问内核数据。
3. Cortex-M0+ 只有 8 个 region，留出余量。

**后果**：
- ⚠️ 任务数量受 region 数限制（M0+ 上约 4–6 个受保护任务）。超出时退化为"仅保护内核数据 + 当前任务守卫"。
- ⚠️ 任务间共享数据不隔离（都在同一地址空间）→ 用 Rust 类型系统 + 明确的共享 API（`echo-sync`）约束。
- ✅ 上下文切换无 MPU 开销（除非切换栈守卫）。
- ✅ 为将来在 Cortex-M33 (TrustZone) 上做硬件强隔离留了结构。

## ADR-0006 · 临界区使用 `BASEPRI` 而非 `PRIMASK`

**状态**：已决定

**背景**：内核需要保护共享数据结构的临界区。Cortex-M 提供 `PRIMASK`（屏蔽全部可配置优先级中断）与 `BASEPRI`（屏蔽优先级数值 ≥ 阈值的中断）。

**候选**：`PRIMASK` / `BASEPRI` / 自旋锁。

**决定**：**`BASEPRI` 为默认**，`echo-critical` 封装为 RAII guard。

**理由**：
1. `PRIMASK` 会把**所有**中断（包括与内核数据无关的高优先级实时中断）一起延迟，直接伤害 G1（实时性）。
2. `BASEPRI` 只屏蔽"会访问同一份内核数据的中断"，其它中断照常响应。
3. RAII guard 保证恢复路径不遗漏（包括 panic 路径）。

**后果**：
- ⚠️ 需要一套**中断优先级分配规范**：哪些中断优先级高于"内核临界区屏蔽线"、哪些低于。这是 BSP 配置的一部分，需文档化。
- ⚠️ 驱动 ISR 若访问内核 API，其优先级必须低于屏蔽线。需在编译期或启动时校验（`echo-driver` 提供断言）。
- ✅ 高优先级实时中断的延迟不受内核活动影响。

## ADR-0007 · 编译期静态配置（const + cfg），不用运行时配置

**状态**：已决定

**背景**：RTOS 传统上提供 Kconfig 或运行时配置选项。

**候选**：
- A. 运行时配置结构体（FreeRTOS 部分 API 风格）
- B. 自定义 Kconfig 风格 DSL
- C. **Rust `const` + `cfg` + const 泛型**

**决定**：C。

**理由**：
1. 静态配置让编译器可以做常量折叠、死代码消除、数组大小确定——直接服务于 G3（可裁剪）和 G5（低占用）。
2. 无需额外工具链（对比 Zephyr 的 Kconfig/devicetree 学习成本）。
3. 类型系统可以校验配置合法性（如 `const_assert!(STACK_SIZE % 8 == 0)`）。
4. 配置错误在编译期暴露，而非运行时报错。

**后果**：
- ⚠️ 改配置需重新编译（对 RTOS 而言这是可接受的，甚至是期望的）。
- ⚠️ 缺乏"配置文件"的直观性 → 由 BSP 提供带文档的常量定义模块缓解。
- ✅ 零运行时配置解析开销，零配置数据结构 RAM 占用。

## ADR-0008 · 默认无堆；需要时提供确定性分配器

**状态**：已决定

**背景**：动态分配是实时系统不确定性的经典来源（碎片 + 不可预测的最坏时间）。

**候选**：
- A. 完全无堆，一切静态
- B. 提供通用堆（`linked_list_allocator` 之类）
- C. **默认无堆；按需选择固定块内存池（O(1)）或 TLSF 堆（O(1) 最坏情况）**

**决定**：C。

**理由**：
1. 任务栈、TCB、同步对象**全部静态分配**——生命周期与程序相同，没有理由动态化。
2. 消息传递、协议缓冲区等动态大小的需求，用固定块内存池即可满足多数场景，且**完全无碎片**。
3. 需要真正变长分配时（如文件系统缓存），TLSF 提供**有界的**最坏情况分配时间（O(1)），远优于传统 malloc。
4. `#[global_allocator]` 支持作为最后选项，`alloc` feature 控制。

**后果**：
- ⚠️ `Box`/`Vec` 在默认配置下不可用。IPC 的所有权传递需通过内存池句柄（`PoolBox<T>`）实现。
- ✅ 分配延迟有界且可测量，服务于 G1。
- ✅ 无碎片，长时间运行不退化。

## ADR-0009 · 互斥量默认使用优先级继承协议（PIP）

**状态**：已决定

**背景**：优先级反转可能导致高优先级任务被无限期阻塞（Mars Pathfinder 的著名故障）。

**候选**：无保护 / 优先级继承（PIP）/ 优先级天花板（PCP）。

**决定**：**PIP 为默认**，PCP 作为可选的编译期配置。

**理由**：
1. PIP 的阻塞时间有界：最多被一个低优先级临界区阻塞一次。
2. PIP 不影响不产生竞争的临界区（无开销）。
3. PCP 的阻塞界更紧，但需要**静态确定每个资源的最高使用者优先级**——在 Rust 中这可以由类型系统辅助表达（资源类型携带优先级参数），作为进阶选项。

**后果**：
- ⚠️ PIP 需要调度器与互斥量协同：`echo-sync` 依赖 `echo-sched` 的优先级调整接口。
- ⚠️ 优先级继承会增加上下文切换次数 → 需要 `echo-bench` 度量其影响。
- ✅ 杜绝无界优先级反转。

## ADR-0010 · 只依赖 stable Rust，不引入 nightly

**状态**：已决定（依赖 Rust 1.88+）

**背景**：嵌入式 Rust 历史上需要 nightly 才能写 OS（`naked_functions`、`asm_const`、`const_refs_to_static` 等）。

**决定**：**只使用 stable Rust**，`rust-version = "1.88"`（当前工具链 1.98.1）。

**理由**：
1. `#[unsafe(naked)]` + `naked_asm!` 已于 **Rust 1.88.0（2025-06-26）稳定**，上下文切换不再需要 nightly。
2. stable 意味着：可复现构建、无跟踪 nightly 变更的维护负担、企业环境易采纳、认证路径更短。
3. 需要 nightly 的特性（如某些 const 泛型能力）可以用替代设计规避。

**后果**：
- ⚠️ 某些"更优雅"的写法可能不可用，需要 workaround。
- ✅ 工具链固定，CI 稳定，贡献者门槛低。

## ADR-0011 · 启动代码、向量表与寄存器定义全部自研

**状态**：已决定（由 [ADR-0014](#adr-0014--零外部-crate-依赖l1-完全自研) 的 L1 策略推导而来）

**背景**：RTOS 必须自己掌控向量表内容、`SVC`/`PendSV`/`SysTick` 处理函数、MSP/PSP 初始化、`.data`/`.bss` 初始化时机（需要在进入 `main` 之前创建静态任务）。这些在 `cortex-m-rt` 的职责范围内，因此该 crate 从一开始就不可用。寄存器访问层的取舍则是 L1 决策的直接结果。

**候选**：
- A. 自研启动 + 复用 `cortex-m` 的寄存器封装与内在函数
- B. **自研启动 + 自研寄存器定义（经 SVD 代码生成）** ← 选定
- C. 自研启动 + 手写全部寄存器定义

**决定**：**B**。启动代码、向量表、链接脚本、寄存器定义全部自研；寄存器定义通过自研的 `svdgen` 从 CMSIS-SVD 生成，不手写。

**理由**：
1. 启动与异常向量是 RTOS 的核心职责，没有复用空间（A 和 B 在此一致）。
2. A 与 B 的分歧只在寄存器层。选定 B 的原因不是"复用有技术问题"，而是 **L1 策略的一致性与收益**（[ADR-0014](#adr-0014--零外部-crate-依赖l1-完全自研)）：零供应链风险、零许可证兼容问题、每个字节可审计。
3. C（手写寄存器）被否决——见 [ADR-0015](#adr-0015--寄存器定义通过自研-svdgen-代码生成)。手写数千个位域是纯负债：错误静默、无法审查、每换一颗芯片重来一次。

**后果**：
- ⚠️ 需自行维护 linker script（`link.x`）与 `memory.x` 模板。
- ⚠️ 需自行实现 `NVIC` / `SCB` / `SysTick` / `MPU` / `DWT` 的访问层，以及内存屏障、`wfi`/`wfe` 等内在操作。
- ⚠️ 失去 `cortex-m` 的 crate 级测试与社区验证 → 由 `echo-regs` 的自研生成器测试 + 硬件回归弥补。
- ✅ 对启动流程、异常向量、内存布局、寄存器访问有完全控制。
- ✅ 换芯片只需换 SVD 文件，不依赖任何 PAC crate 的存在与维护状态。

## ADR-0012 · QEMU 作为第一公民的测试平台

**状态**：已决定

**背景**：嵌入式开发传统上依赖真机，调试成本高、CI 无法自动化。

**决定**：**QEMU 上的自动化测试与真机测试同级**。CI 的主测试套件跑在 QEMU 上。

**理由**：
1. QEMU 可脚本化、可进 CI、无需硬件。
2. Semihosting 可以从 QEMU 内输出测试结果并被 host 捕获 → 完整的断言框架。
3. 覆盖两个架构（Cortex-M 与 RISC-V）只需两个 QEMU 目标，验证了 ADR-0002 的抽象是否真的可移植。
4. **注意**：QEMU 的时序是模拟的，**不能**用 QEMU 做延迟基准的绝对值判定，只能做逻辑正确性验证与趋势对比。绝对延迟必须在真机上测。

**后果**：
- ⚠️ 必须优先安装 `qemu-system-arm` / `qemu-system-misc`（当前环境缺失）。
- ⚠️ QEMU 与真机的差异（缓存、Flash 等待周期、时钟精度）需要在文档中明确。
- ✅ CI 可覆盖完整功能回归，只有实时性指标需要真机。

## ADR-0013 · 许可协议：MIT OR Apache-2.0 双许可

**状态**：待确认

**背景**：Rust 生态惯例（与 Rust 语言本身一致）。

**决定**：建议 `MIT OR Apache-2.0`。

**理由**：Rust 生态惯例，Apache-2.0 含专利授权条款，MIT 更简洁，使用者可二选一。

> 注：在 [ADR-0014](#adr-0014--零外部-crate-依赖l1-完全自研) 的 L1 策略下，许可证兼容性不再是约束（无第三方依赖需要审计）。本决策现在**纯粹是对外发布策略**，可自由选择——若希望最大化采纳度，双许可是安全默认。

**后果**：需在根目录放置 `LICENSE-MIT` 与 `LICENSE-APACHE`，每个 crate 的 `Cargo.toml` 声明 `license.workspace = true`。**需项目所有者确认。**

## ADR-0014 · 零外部 crate 依赖（L1 完全自研）

**状态**：已决定

**背景**：嵌入式 Rust 生态已高度成熟——`cortex-m`、`embedded-hal` 1.0、`defmt`、`heapless`、`smoltcp` 等 crate 覆盖了从寄存器访问到 TCP/IP 的全部层次。是否复用它们，决定了项目的工作量与长期维护成本。

**候选**：

| 层次 | 含义 | 相对工作量 |
| --- | --- | --- |
| L1 | **完全自研，零外部 crate** ← 选定 | ×10 |
| L2 | 复用架构封装（`cortex-m`），自研内核逻辑 | ×1 |
| L3 | 复用 `cortex-m-rt` 运行时 | ×0.6 |
| L4 | 包装现有 RTOS（FreeRTOS/Zephyr） | ×0.2 |

**决定**：**L1**——`[dependencies]` 中外部 crate 数量恒为 0，由 `cargo xtask lint-deps` 强制。

**理由**：
1. **完全可控与可审计**：镜像中的每一行代码都是自己的。出现任何问题时，根因一定在仓库内，不存在"第三方 crate 的黑盒行为"。
2. **零供应链风险**：不依赖任何上游 crate 的维护状态、版本策略、或被弃用/被收购的风险。
3. **零许可证兼容问题**：无第三方许可证需要审计或合规。
4. **教学与研究价值**：作为"从零构建 RTOS"的完整参考实现，这个价值只有在真正从零时才成立。
5. 这是项目所有者的明确决策。

**后果 —— 必须正视的成本**：

| 代价 | 严重度 | 缓解 |
| --- | --- | --- |
| 工期延长约一个数量级 | 高 | 分阶段交付（M0–M6 先做内核，服务层全部推迟）；[SVD 代码生成](#adr-0015--寄存器定义通过自研-svdgen-代码生成)消除最大的那块工作量 |
| **第三方 `embedded-hal` 驱动无法直接使用** | 高 | 长期成本，非一次性。自研 HAL trait 保持与 `embedded-hal` **概念对齐**，降低移植成本 |
| **网络栈需自研 → 首版无 TCP/IP** | 高 | 通用 TCP/IP 已列为非目标；**现场总线（EtherCAT/CAN-FD）是主干**，见 [Q8](09-risks-and-open-questions.md#q8--现场总线选型--最高优先级) |
| 失去社区验证过的代码 | 中 | 自研部分的测试覆盖要求提高；硬件回归（HIL）频率提高 |
| `defmt` 等工具链需自研 | 中 | 首版用简单的 UART 文本日志，结构化日志推迟 |

**复议条件**（出现以下任一情况时，应重新评估本决策）：
- M2 结束时，实际进度落后计划 3 倍以上
- 目标场景明确要求 TCP/IP，且无法推迟
- 项目从"从零构建"的教学/研究定位转向产品交付

## ADR-0015 · 寄存器定义通过自研 `svdgen` 代码生成

**状态**：已决定（ADR-0014 的**使能条件**——没有它，L1 不可行）

**背景**：在 L1 下，寄存器定义必须自研。一颗 STM32F4 有约 100 个外设、数千个寄存器、上万个位域。手写是不可能的。

**候选**：
- A. 手写全部寄存器与位域定义
- B. 从 CMSIS-SVD 生成（自研生成器）
- C. 首版只手写用到的少数寄存器，随用随加

**决定**：**B**。

**理由**：

1. **手写（A）的代价被严重低估**。不只是"数万行"的问题：
   - 位域的偏移量、宽度、枚举值错误是**静默的**——编译通过，运行时行为诡异，且极难定位。
   - 无法审查：没有人能人工核对一万个位域的偏移是否正确。
   - 每支持一颗新芯片都要重来一遍。
2. **CMSIS-SVD 是厂商发布的公开硬件描述标准**（ARM CMSIS 规范），不是软件依赖。使用它等同于查阅芯片参考手册，不违反 L1 的"零外部 crate"约束。
3. **`svdgen` 是我们自己的代码**：生成逻辑、模板、错误处理全部自研。产物也是自研代码，只是由程序而非人手写出。
4. **错误集中在一个可测试的点上**：生成器写对一次，所有芯片受益；生成器的测试可以覆盖全部边界情况。

**实现要点**：

```
vendor.svd (XML)  ──►  svdgen  ──►  echo-<chip>-regs/src/*.rs
                       │
                       ├─ XML 解析（自研，无 quick-xml 等依赖）
                       ├─ 寄存器/位域/枚举建模
                       ├─ 中断号表 → 枚举
                       ├─ 地址对齐与重叠校验
                       └─ 生成 UnsafeCell 封装（不用 vcell）
```

- **生成的代码检查进版本库**：可审计、可 diff、可手工修正厂商 SVD 的错误（SVD 确实常有小错）。
- **生成器自身的测试**：用手写的微型 SVD 夹具验证解析与生成逻辑，覆盖寄存器数组、派生外设（`derivedFrom`）、重复位域、保留位等场景。
- **不引入 XML 解析 crate**：SVD 的 XML 子集很小，自研一个够用的解析器约 300 行。

**后果**：
- ⚠️ 前期投入：生成器约 2000 行 + 测试，约数周。**这是整个 L1 决策中最关键的一笔投资。**
- ⚠️ 需自行处理 SVD 的不规范之处（厂商差异、`derivedFrom` 继承、命名不统一）→ 生成器需容错与告警。
- ✅ 换芯片成本从"数月手写"降为"换一个 SVD 文件 + 跑一次生成"。
- ✅ 位域错误率从"人手不可控"降为"生成器测试可覆盖"。

## ADR-0016 · 循环执行体作为一等调度模式

**状态**：已决定（由 [02 §2.8.2](02-embodied-ai-robot-profile.md#282-多速率确定性循环执行体-vs-优先级抢占-阶段一) 推导）

**背景**：[ADR-0004](#adr-0004--线程模型作为调度基础async-仅作可选适配层) 确定以优先级抢占线程为调度基础。但机器人的多速率控制负载有更强的确定性要求：

| 特性 | 优先级抢占 | 静态循环执行体 |
| --- | --- | --- |
| 抖动来源 | 抢占时机取决于事件到达 | **零**——调度表编译期确定 |
| 可分析性 | 需响应时间分析（RTA） | **直接读出** |
| 突发负载弹性 | 好 | 无（超限即错） |
| 适用 | 事件驱动、混合负载 | **严格周期、多速率控制** |

**决定**：**两种模式同时提供，且在同一系统中共存**。

- `echo-sched` 提供 `CyclicExecutive<SCHEDULE>`，`SCHEDULE` 是 **const 泛型**的编译期调度表
- **循环执行体域**：控制律、插值、安全校验、传感器处理 → 严格周期性，零抖动
- **抢占任务域**：通信、诊断、日志、shell、文件系统 → 事件驱动，可容忍抖动
- 跨域通信通过 `echo-ipc` 的有界队列，非阻塞发送

**理由**：

1. **纯抢占式无法满足多速率控制的抖动要求**。tick 驱动的调度抖动达一个 tick 周期（1 kHz tick → 1 ms），完全不可接受。
2. **静态调度表是 [ADR-0007](#adr-0007--编译期静态配置const--cfg不用运行时配置) 哲学的自然延伸**。调度表是编译期常量，可用 `const_assert!` 做部分合法性校验（槽位不重叠、总周期不超限）。
3. **两种模式解决不同问题，不应二选一**。控制域需要确定性，服务域需要弹性。

**后果**：
- ⚠️ 调度器复杂度上升：两套机制 + 明确的边界规则。**边界必须写进文档并在 review 中检查**，否则会退化为"到处都能挂周期任务"。
- ⚠️ 循环执行体的槽位超限处理需要设计：检测、记录、降级策略（[R12](02-embodied-ai-robot-profile.md#27-对-echoos-的架构要求)）。
- ✅ 控制域的抖动从"依赖于事件到达模式"变为"编译期确定"。
- ✅ 为功能安全认证提供了可分析性基础（静态调度比抢占式容易论证得多）。

## ADR-0017 · AI 命令是"建议"，安全层是不可绕过的仲裁者

**状态**：已决定（**架构不变式**）｜ **实施阶段：阶段三**

> ⏩ **本 ADR 现在只固化不变式，不在阶段一实施。** 决策本身已定，且**依赖规则现在就要落地**（`echo-bridge` 不得被 `echo-safety` 以下任何层依赖）。但 `echo-bridge` / `echo-safety` 的实现属于 **阶段三（AI 接入）**——见 [02 §2.3](02-embodied-ai-robot-profile.md#23-分阶段交付策略-) 与 [ADR-0019](#adr-0019--分阶段交付实时控制优先)。
>
> **理由**：AI 安全层的意义完全建立在确定性底座之上。底层的抖动不受控时，任何安全包络的计算都是流沙上的建筑。

**背景**：具身智能机器人的上层是**非确定性的 AI 栈**（Linux + 大模型），它会产生不安全的、迟到的、不存在的、格式错误的命令。而执行器是物理的，机器人是人机共处的系统。

**候选**：
- A. 信任 AI 输出，直接下发到执行器（多数现有方案的事实做法）
- B. 在 AI 侧做安全校验（同进程，无隔离）
- C. **在 RTOS 侧设立不可绕过的仲裁层** ← 选定
- D. 硬件安全电路独立于软件（成本高，且无法表达复杂约束如工作空间）

**决定**：**C**。实现 [02 §2.8.1](02-embodied-ai-robot-profile.md#281-ai-与硬实时的边界安全包络与命令仲裁--阶段三) 的三层防护：

```
AI 栈 ──► echo-bridge ──► echo-safety ──► echo-motion ──► fieldbus ──► 关节
            传输边界        语义边界        时间边界
            （完好性）      （安全性）      （连续性）
```

**核心原则**：

> **AI 的输出是建议（proposal），不是命令（command）。安全层永远有一条"当前安全轨迹"在跑——AI 失联只会让它平滑减速，不会让它失控。**

**理由**：

1. **物理安全不能依赖一个每月都在变化的 AI 栈**。软件栈的演进速度与安全要求的速度不匹配，必须有稳定边界。
2. **同地址空间的校验等于没有校验**（方案 B）。AI 进程的 bug 会直接写坏校验逻辑。
3. **满足功能安全的"自由度内失效"**：AI 域的失效不得传播到安全域。
4. **优雅降级是工程必需**：AI 崩了机器人应该停下来，而不是摔下去。

**后果**：
- ⚠️ **增加端到端延迟**：AI 命令必须经过校验与插值才能到达执行器。约 1 个控制周期的额外延迟（1 kHz 下 1 ms）——对 1–50 Hz 的 AI 命令完全可接受。
- ⚠️ **`echo-bridge` 与 `echo-safety` 之间绝不能出现反向依赖或旁路** —— 由 `xtask lint-deps` 校验单向链（[风险 T22](09-risks-and-open-questions.md#910-具身智能机器人场景引入的新风险)）。
- ⚠️ 安全限值需要与机器人本体参数绑定（关节限位、连杆长度、质量），这些是**编译期常量**，换机器人需重新编译（符合 [ADR-0007](#adr-0007--编译期静态配置const--cfg不用运行时配置)）。
- ✅ **这是现有 RTOS 都不提供的能力** —— `FreeRTOS`/`Zephyr` 抽象的是任务与资源；`ros2_control` 把该逻辑放在 Linux 应用层，无硬实时保证且无隔离。
- ✅ 使 EchoOS 从"更快的 RTOS"变成"为具身智能而设计的 RTOS"。

## ADR-0018 · 内存分层：TCM 放实时代码与数据，缓存属性显式声明

**状态**：已决定（由 [02 §2.8.3](02-embodied-ai-robot-profile.md#283-缓存与-tcmcortex-m7-的现实-阶段一) 推导）

**背景**：机器人关节控制器的主流平台是 **STM32H7（Cortex-M7 @ 480 MHz，带 D-Cache + TCM）**。原方案的示例平台是 Cortex-M3/M4（无 D-Cache），完全没有覆盖缓存一致性问题。

在 480 MHz 的 M7 上，**一次 D-Cache Miss 的代价可能超过整个上下文切换时间**——这直接威胁 [02 §2.5](02-embodied-ai-robot-profile.md#25-实时需求的量化) 的抖动目标。

**决定**：

1. **硬实时资产优先放入 TCM**（零等待、不可缓存）：
   - ITCM：中断向量表、控制律代码、`PendSV`/`SVC`/异常入口
   - DTCM：硬实时任务的栈、控制用实时数据、DMA 缓冲区
2. **MPU region 必须显式声明缓存属性**（`TEX`/`C`/`B`/`S`），[ADR-0005](#adr-0005--单地址空间--mpu-静态分区) 的静态分区扩展为"分区 + 缓存属性"的联合配置
3. **DMA 缓冲区默认走非缓存区**；若必须在缓存区，则强制使用配对的 clean/invalidate API（API 设计上让"忘记 invalidate"变得困难）
4. **提供 `#[echo::tcm]` 属性宏**，把函数/静态变量放入指定 TCM 段

**理由**：

1. 抖动是机器人的第一指标（[02 §2.5](02-embodied-ai-robot-profile.md#25-实时需求的量化)），而 cache miss 是抖动的主要来源之一，且**不可预测**。
2. DMA 与 D-Cache 不一致是**静默的数据损坏**，只在特定时序下出现——这类 bug 的调试成本极高，必须在设计上消除而非靠测试发现。
3. 静态分区方案（ADR-0005）本身就是"启动时配置一次"的，扩展缓存属性**不增加运行时开销**。

**后果**：
- ⚠️ 链接脚本必须支持 TCM 段划分（`link.x` 复杂度上升）。
- ⚠️ `echo-mm` 需要新增 TCM 分配器与内存区域属性模型。
- ⚠️ 换芯片时 TCM 大小与地址不同（H743: 64 KB ITCM + 128 KB DTCM），需 BSP 配置。
- ✅ 消除了抖动的一大来源，使 [02 §2.5](02-embodied-ai-robot-profile.md#25-实时需求的量化) 的抖动目标成为可能。
- ✅ DMA 一致性由架构保证，而非靠开发者记忆。

## ADR-0019 · 分阶段交付，实时控制优先

**状态**：已决定（**本方案最重要的范围约束**）

**背景**：具身智能机器人的完整愿景包含 AI 接入，但那是一个**依赖关系极强的上层**。同时启动全部工作会导致：范围失控、接口反复重写、长期没有可交付成果。

**决定**：分三阶段交付，**当前专注阶段一**。

| | 阶段一 · 实时控制内核 | 阶段二 · 机器人运动控制 | 阶段三 · AI 接入 |
| --- | --- | --- | --- |
| **crate** | `core/*` `arch/*` `regs/*` `kernel/*` `api/*` `services/driver,hal` | `echo-fieldbus` `echo-can` `echo-motion` `echo-sensor` | `echo-bridge` `echo-safety` |
| **关键验证** | **V1 单关节切片**（示波器测抖动） | **V2 双节点切片**（总线同步精度） | 故障注入（AI 崩溃/超时/越限） |
| **产出** | 能跑 BLDC 电机、抖动可量化、零依赖的 RTOS | 多关节机器人能协调运动 | AI 能安全驱动机器人 |

**理由**：

1. **逻辑依赖**：`echo-safety` 的保证前提是**执行层行为可预测**。抖动不受控时，安全包络的计算没有意义。
2. **阶段一独立可交付**：一个能在 STM32H7 上跑电机控制、抖动可量化、零依赖的 Rust RTOS，**不需要 AI 就有价值**。这直接缓解 [风险 P1](09-risks-and-open-questions.md#92-项目风险)（范围过大）。
3. **AI 侧技术栈每几个月变一次**，作为第一优先级会导致接口反复重写（[风险 T24](09-risks-and-open-questions.md#910-具身智能机器人场景引入的新风险)）。

**后果**：
- ✅ 项目在任何阶段都有可交付、可演示的成果。
- ✅ 阶段一的风险（抖动是否达标、`svdgen` 是否可行）最早暴露。
- ⚠️ **阶段三的不变式必须现在就固化**：`echo-bridge` 不得被 `echo-safety` 以下任何层依赖，由 `xtask lint-deps` 校验。否则等阶段三再补，架构已经被污染。
- ⚠️ 阶段一之外的设计保留在文档中，但**必须明确标注阶段归属**，避免污染当前决策。
- ⚠️ 阶段二的现场总线选型（[Q8](09-risks-and-open-questions.md#q8--现场总线选型--最高优先级)）**仍需尽早决策** —— 它决定 `echo-fieldbus` 的抽象是否够用。但**不阻塞阶段一**。
