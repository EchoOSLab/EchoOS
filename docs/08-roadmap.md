# 08 · 里程碑规划

## 8.1 规划原则

1. **分阶段交付，实时控制优先**（[ADR-0019](05-design-decisions.md#adr-0019--分阶段交付实时控制优先)）。阶段一之外的工作不进入当前里程碑。
2. **每个里程碑都有可演示的产出。** 不接受"完成了 80% 的调度器"这种状态——要么能跑，要么没完成。
3. **测试与基准与功能同步建设，不留到最后。** L2 测试层（host 上的内核逻辑测试）从 M0 就要建立，否则 [ADR-0002](05-design-decisions.md#adr-0002--内核泛型化-over-arch-trait) 的架构收益会落空。
4. **每个阶段以一个垂直切片收尾**，用真实硬件验证最关键的假设。**纸面分析不能替代示波器读数。**
5. **工期是相对量级，不是承诺。** 标注 S（1 周内）/ M（1–3 周）/ L（1–2 月）/ XL（2 月+），按单人全职估算。

## 8.2 里程碑总览

```
╔══════════════════════ 阶段一 · 实时控制内核（★ 当前专注）══════════════════════╗
║                                                                            ║
║  M0 ──► M1 ──► M2 ──► M3 ──► M4 ──► M5 ──► M6 ──► M7                       ║
║  骨架   启动   调度   时间   同步   内存   驱动   实时控制闭环                 ║
║   M      L      L      M      L      L      L      L                       ║
║                  │                        │         │                       ║
║            循环执行体                  第二架构    V1 单关节切片             ║
║            （零抖动）                  RISC-V      ★ 用示波器测抖动          ║
║                                                                            ║
╚════════════════════════════════════════════════════════════════════════════╝
                                    │
                                    ▼  产出：能跑电机、抖动可量化、零依赖的 RTOS
╔═════════════════ 阶段二 · 机器人运动控制 ══════════════════╗
║  M8 现场总线 ──► M9 多关节协调                             ║
║   L / XL+          XL                                     ║
║        │              │                                   ║
║        └──── V2 双节点切片 ★ 总线同步精度 ────┘             ║
╚═══════════════════════════════════════════════════════════╝
                    │
                    ▼  产出：多关节机器人能协调运动
╔═════════════════ 阶段三 · AI 接入 ══════════════════╗
║  M10 AI 桥接 ──► M11 安全包络与命令仲裁              ║
║   L                L                               ║
║        └── V3 故障注入 ★ AI 崩溃/超时/越限 ──┘       ║
╚════════════════════════════════════════════════════╝
                    │
                    ▼  产出：AI 能安全驱动机器人

后续可选（可与阶段三并行）：M12 服务层 · M13 用户态
```

**规模注释**：

- 按 L1 策略（[ADR-0014](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研)）调整：M1 由 S 上调至 L（寄存器层入场费）
- **相对早期方案的最大变化**：把"实时控制闭环"提为 **M7 —— 阶段一的终点**，而不是等到最后。理由见下。

### ★ 垂直切片：本路线图最重要的方法论调整

早期方案是**水平分层、自底向上**：先把内核做完整，再往上搭。这有一个致命问题：

> **最关键的假设——抖动够不够、ISR 内跑控制律行不行、总线同步精度够不够——从未被验证，却已经在它们之上建了数年的代码。**

**对策：每个阶段以一个垂直切片收尾**，用最小的代价提前验证该阶段最关键的假设。

| 切片 | 位置 | 内容 | 验证什么 | 失败时的处置 |
| --- | --- | --- | --- | --- |
| **V1 单关节** | **M7**（阶段一终点） | 定时器 → ISR 采 ADC → 控制律 → PWM → 电机转起来 | **抖动预算是否成立**；ISR 内跑控制律是否可行 | 控制律入 ITCM → 栈入 DTCM → 关 D-Cache 对比 → 重审临界区 → 最后才降频 |
| **V2 双节点** | **M9**（阶段二终点） | 协调节点 → 总线 → 关节节点 → 闭环 | 总线同步精度；端到端延迟；节点丢失检测 | 换总线方案 / 调整同步协议 |
| **V3 故障注入** | **M11**（阶段三终点） | AI 崩溃 / 超时 / 越限命令 | 安全层是否真的不可绕过 | 修安全层——**这个阶段绝不能通过"降低要求"来收场** |

**这三个切片都是独立的里程碑终点，而不是附加验收项。** 它们决定了"能不能继续往下走"。

> **V1 是整个项目的"物理可行性证明"。** 在纸面上讨论抖动预算是抽象的；让电机转起来、用示波器测出分布，才是真的。**如果 V1 失败，M8–M11 全都失去意义** —— 所以它必须早做。

## M0 · 骨架就位

**规模**：M（因 L1 决策从 S 上调——增加了 `svdgen` 骨架与 `echo-vcell`）｜ **前置**：无

**目标**：工程结构、工具链、CI、测试基础设施全部就位，**并验证 `svdgen` 可行**。不写任何内核逻辑。

**交付物**：
- [ ] 工具链补齐（`rustup target add` × 4、QEMU、`cargo-deny`/`geiger`/`binutils`）
- [ ] workspace 骨架：根 `Cargo.toml`（含 `default-members`）、`rust-toolchain.toml`、`.cargo/config.toml`、`rustfmt.toml`、`deny.toml`
- [ ] 从当前单 crate 迁移：删除 `src/main.rs` 与 `[package] echoos`，改为虚拟 workspace 清单
- [ ] `echo-util` 骨架 + 至少 `bitmap.rs` 与 `intrusive_list.rs` 实现（带单元测试）
- [ ] ★ `echo-vcell`：寄存器内部可变性封装（`echo-util` 与寄存器层的共同前置）
- [ ] ★ `tools/svdgen` 骨架：能解析一个 SVD 并生成一个外设（**验证 [A7](09-risks-and-open-questions.md#94-需要重点验证的假设) 的最小闭环**）
- [ ] `echo-arch-api`：`trait Arch` 定义（可先不定稿）
- [ ] `echo-arch-mock`：`MockArch` 最小实现
- [ ] `xtask`：`setup` / `build` / `test --layer host` / `lint-deps` 四个子命令
- [ ] GitHub Actions：`fmt` + `clippy` + `test(host)` + `lint-deps` + `size`
- [ ] `tools/scripts/setup.sh`

**验收标准**：
1. `cargo xtask setup` 幂等执行成功，环境检查全绿
2. `cargo test` 在 host 上通过（跑 `echo-util` 的单元测试）
3. `cargo xtask lint-deps` 能检出**两类**故意注入的违规：跨层依赖（R1）**与外部 crate 依赖（R7）**
4. **★ `svdgen` 能用目标芯片的真实 SVD 生成一个外设的寄存器代码，且该代码通过 `cargo check`** —— 这验证了 [假设 A7](09-risks-and-open-questions.md#94-需要重点验证的假设)，是整个 L1 策略的可行性闸门
5. CI 全绿

**风险**：多 crate + `default-members` 的配置容易反复试错。**先在一个最小 workspace（3 个 crate）上验证构建矩阵，再铺开。**

## M1 · 最小可运行内核

**规模**：**L**（因 [ADR-0014](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研) 的 L1 决策从 M 上调）｜ **前置**：M0

**目标**：QEMU 上启动 EchoOS，串口输出启动日志，进入 idle。**这是"它活了"的时刻。**

**交付物（★ = L1 特有，在 L2 方案中不存在）**：
- [ ] ★ `tools/svdgen`：SVD → Rust 代码生成器（XML 解析 + 建模 + 代码生成 + 夹具测试）
- [ ] ★ `echo-stm32f4-regs`：svdgen 的生成产物（首个验证目标）
- [ ] ★ `echo-cortex-m-regs`：NVIC / SCB / SysTick / MPU / DWT（手写，规模小且稳定）
- [ ] ★ `echo-atomic`：原子抽象（M3+ 原生 CAS）
- [ ] `echo-vcell`：在 M0 骨架基础上补全（生成代码依赖它）
- [ ] `echo-arch-cortex-m`：Reset 流程、向量表、`link.x`、`memory.x` 模板
- [ ] `echo-rt`：`.data`/`.bss` 初始化、panic handler、`#[echo::main]` 宏
- [ ] `echo-trace`：串口输出后端（自研，无 `defmt`）
- [ ] `echo-bsp-qemu-cortex-m`：QEMU mps2-an385 的 BSP
- [ ] `echo-time`：只读时基（`Instant::now()`），无定时器
- [ ] 启动流程骨架（[03 §3.5.4](03-architecture.md#354-启动流程) 的步骤 1–7，任务创建留待 M2）

**验收标准**：
1. `cargo xtask run --bsp qemu-cortex-m` 在 QEMU 中输出：
   ```
   [INFO ] EchoOS v0.1.0 booting...
   [INFO ] arch: cortex-m3 @ qemu-mps2-an385
   [INFO ] clock: 25 MHz, tick source: systick
   [INFO ] kernel: initialized, entering idle
   ```
2. 进入永久 idle 循环（`wfi`），无异常
3. `cargo xtask size` 报告 Flash < 8 KB
4. 故意触发 panic 时，输出任务名、PC/LR、栈回溯

**关于自举顺序**：在 [ADR-0014](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研) 的 L1 策略下，没有 `cortex-m-rt` 可以"先借用一下"——从第一天起就是自研。这消除了替换风险，但**要求 M1 一开始就投入 `svdgen` 与 `echo-cortex-m-regs`**（见 ADR-0015）。

**M1 内部建议顺序**：

```
1. svdgen 骨架 + 微型 SVD 夹具测试        ← 先让生成器能跑通
2. 生成 STM32F401 寄存器 crate（验证生成器）
3. echo-cortex-m-regs（NVIC/SCB/SysTick 手写，规模小）
4. echo-vcell + echo-atomic（被上面依赖）
5. link.x + 向量表 + Reset 流程
6. echo-trace + UART 输出 → 看到第一个字符
```

第 1–4 步是 L1 特有的前置工作，**在 L2 方案中不存在**。这是 L1 的主要前期成本。

## M2 · 调度器与上下文切换 ★ 关键里程碑

**规模**：L ｜ **前置**：M1

**目标**：多任务抢占式调度在 QEMU 上正确运行。**这是内核从"能启动"变成"是操作系统"的分界点。**

**交付物**：
- [ ] `echo-arch-cortex-m`：`PendSV` / `SVC` / `SysTick` 的 `naked_asm!` 实现、MSP/PSP 双栈、栈帧布局
- [ ] `echo-arch-mock`：完整的 `switch_context` 模拟（可记录调用序列）
- [ ] `echo-macros`：`#[echo::task]` —— 生成静态 TCB + 栈 + 注册到 `.echo_tasks` 段
- [ ] `echo-sched`：就绪位图 + 队列、`O(1)` 最高优先级查找、同优先级 RR
- [ ] ★ **`echo-sched`：循环执行体 `CyclicExecutive<SCHEDULE>`**（[ADR-0016](05-design-decisions.md#adr-0016--循环执行体作为一等调度模式)，[02 §2.8.2](02-embodied-ai-robot-profile.md#282-多速率确定性循环执行体-vs-优先级抢占-阶段一)）——编译期静态调度表，控制域零抖动
- [ ] `echo-critical`：`BASEPRI` RAII guard
- [ ] `echo-kernel`：`Kernel<A: Arch>` 门面 + 首次调度入口
- [ ] idle 任务
- [ ] **L2 测试套件**：不少于 15 个 host 上的调度语义测试
- [ ] **`echo-bench`**：上下文切换时间基准

**验收标准**：
1. **功能**：`examples/02-preemptive-scheduling` 在 QEMU 上产生确定性输出——3 个不同优先级任务按预期抢占顺序打印，重复运行结果一致
2. **语义**（host 测试，不依赖 QEMU）：
   - 高优先级就绪时立即抢占
   - 同优先级任务按 RR 轮转
   - `idle` 仅在无其它就绪任务时运行
   - 优先级变更触发正确的重新调度
3. **实时性**：上下文切换 < 2 µs（QEMU 周期数换算，作为基线）
4. **回归**：`cargo xtask bench` 输出 JSON，CI 与基线对比

**风险**：
- 上下文切换的汇编是**最易出错**的部分，栈帧布局差一个字节就是随机崩溃。**对策**：先用 `echo-arch-mock` 把调度**决策逻辑**测透，再让汇编只负责机械的寄存器搬运；同时用栈魔数（canary）验证栈帧边界。
- 首次任务启动（伪造异常返回帧）是经典难点。**对策**：单独写一个最小测试用例（单任务 + `SVC` 启动），先于多任务场景验证。

## M3 · 时间、多速率与阻塞

**规模**：L（因新增多速率支持从 M 上调）｜ **前置**：M2

**目标**：任务可以睡眠、延时、被定时唤醒；**控制域的任务被硬件定时器精确触发**。

**交付物**：
- [ ] `echo-time`：`Instant`/`Duration`、单调时基（DWT 或定时器）、计数器回绕处理
- [ ] 延时链表（按到期时刻有序）
- [ ] `sleep` / `sleep_until` / `yield_now`
- [ ] 软件定时器（单次/周期），回调在定时器服务任务上下文
- [ ] Tickless 空闲（空闲时关 tick，一次性定时器唤醒）
- [ ] `echo-sched`：`blocked` 模块（延时链表 + 事件等待链表）、`wake_reason` 竞态处理
- [ ] ★ **硬件定时器直接触发**：`CyclicExecutive` 的槽位由定时器事件驱动，**不经 tick**（[02 §2.5](02-embodied-ai-robot-profile.md#25-实时需求的量化)）
- [ ] ★ **槽位超限检测与钩子**（[要求 R12](02-embodied-ai-robot-profile.md#27-对-echoos-的架构要求)）：截止时间错过必须可检测、可观测
- [ ] ★ **时基驯服接口**：本地计数器与外部时钟之间的偏移/速率可调（为阶段二的总线同步预留）

**验收标准**：
1. `examples/06-timer-and-soft-timers`：任务按 10/100/1000 ms 周期运行，实测周期误差 < 1%
2. **超时与事件竞争测试**：构造"事件在超时时恰好到达"的用例，断言 `wake_reason` 正确且节点只被摘除一次（host 测试，用 `MockArch` 精确控制时间推进）
3. Tickless 验证：空闲 1 秒期间的中断次数 < 10（对比 tickful 的 1000 次）
4. 时基回绕测试：用 `MockArch` 模拟 32 位计数器回绕，断言 `Instant` 单调性不受影响

## M4 · 同步与 IPC

**规模**：L ｜ **前置**：M3

**目标**：任务间可以安全地共享数据和传递消息。内核具备实用价值。

**交付物**：
- [ ] `echo-sync`：`Mutex`（含 PIP）、`Semaphore`、`BinarySemaphore`、`EventGroup`、`RwLock`
- [ ] `echo-ipc`：`Queue<T, N>`、`Channel<T>`、`Mailbox<T>`、`Signal`
- [ ] ISR 安全 API（`try_*` / `*_from_isr`）与类型区分
- [ ] `echo-mm` 骨架：固定块内存池（`Pool<T, N>` + `PoolBox<T>`），供 IPC 传递所有权
- [ ] ISR 上下文校验：启动时断言 ISR 优先级与临界区屏蔽线的关系
- [ ] **并发测试套件**：优先级反转、死锁检测（运行时 mutex 持有者追踪）

**验收标准**：
1. **优先级反转测试**（核心验收项）：
   ```
   场景：L 持有 Mutex → H 请求（被阻塞）→ M 就绪（不应能抢占 L）
   断言：H 的阻塞时长 ≤ L 的临界区长度 + 常数开销
   对照：关闭 PIP 时，H 被 M 无限期阻塞（测试应能演示这个差异）
   ```
2. `examples/03-sync-mutex-priority-inheritance` 与 `04-ipc-queue` 在 QEMU 上通过
3. 队列语义测试：满/空边界、`try_send` 归还消息、多生产者多消费者压力测试
4. `Pool` 分配最坏时间 < 100 ns（基准）
5. **`cargo geiger`**：`echo-sync` / `echo-ipc` 的 unsafe 行数为 0（`deny(unsafe_code)` 生效）

**风险**：阻塞/唤醒的竞态是**最难测的 bug 来源**。对策：`MockArch` 提供"精确时间控制"和"中断注入点"，让单个测试能构造出所有交错顺序。

## M5 · 内存管理与栈保护

**规模**：L ｜ **前置**：M4

**目标**：栈溢出被精确捕获而非静默破坏内存；具备变长分配的确定性方案。

**交付物**：
- [ ] `echo-mm`：TLSF 分配器（`O(1)` 最坏情况）、可选 `#[global_allocator]`
- [ ] 任务栈：MPU 守卫区、水位线填充与查询、canary 检查
- [ ] `echo-arch-cortex-m`：MPU region 编程、`MemManage` 异常处理
- [ ] 静态 MPU 分区（[ADR-0005](05-design-decisions.md#adr-0005--单地址空间--mpu-静态分区)）
- [ ] `echo-shell` 骨架：查询任务、栈水位、内存池用量
- [ ] FPU lazy stacking 优化（若目标有 FPU）

**验收标准**：
1. **栈溢出测试**：构造递归耗尽栈的任务
   - 配置 MPU 守卫 → 任务被终止，输出"task X stack overflow at 0x..."，**系统继续运行**
   - 无 MPU 配置 → canary 检测到并报告
2. 栈水位报告准确：实际使用量报告值 ≥ 真实值
3. TLSF 分配最坏时间有界：压力测试下最坏值 < 最坏值的 3 倍（抖动有界）
4. **内存池耗尽测试**：池耗尽时 `alloc()` 返回 `None`，不 panic、不阻塞
5. Miri 通过：`cargo +nightly miri test -p echo-mm -p echo-util`

## M6 · 驱动框架与可移植性验证 ★ 关键里程碑

**规模**：L ｜ **前置**：M5

**目标**：**验证 `Arch` 抽象是否真的可移植**。第二个架构跑通同一套测试。

**交付物**：
- [ ] `echo-driver`：编译期设备树宏、中断绑定、`#[echo::irq]`、上半部/下半部
- [ ] `echo-hal`：**自研** HAL trait 体系（概念对齐 `embedded-hal`，见 [06 §6.6](06-subsystems.md#hal-trait-体系echo-hal)）
- [ ] 各芯片的 `echo-*-regs`：用 `svdgen` 生成（验证"换芯片只换 SVD"这一承诺）
- [ ] 驱动：UART、GPIO、定时器、SPI（全部自研）
- [ ] `echo-arch-riscv`：RV32IMAC 移植（CLINT 定时器、PLIC 中断控制器、机器模式陷出）
- [ ] `echo-bsp-qemu-riscv-virt`
- [ ] `echo-conformance`：跨平台一致性测试套件
- [ ] `echo-bsp-nucleo-f401re`：首个真机 BSP

**验收标准**：
1. **可移植性（核心里程碑）**：`echo-conformance` 套件在 Cortex-M 和 RISC-V 上**全部通过**，且内核 crate 一行未改
   ```
   这直接验证 ADR-0002。如果做不到，说明 Arch trait 抽象泄漏，
   需要回头修改——越早发现代价越小。
   ```
2. `examples/05-driver-uart` 在两个平台上行为一致
3. 一个真实外设（如 I2C 温度传感器）通过 `echo-hal` trait 接入，且驱动代码可在 host 上用 mock 测试
4. ISR 优先级校验生效：故意配置错误优先级 → 启动时 panic 并给出清晰信息
5. 真机验证：STM32H7 上跑通 M2–M5 的全部测试（见 [Q9](09-risks-and-open-questions.md#q9--硬件平台--最高优先级)）

## M7 · 实时控制闭环 ★★ 阶段一的终点

**规模**：L ｜ **前置**：M6

**目标**：**让电机转起来，并用示波器测出真实的抖动分布。** 这是阶段一（[ADR-0019](05-design-decisions.md#adr-0019--分阶段交付实时控制优先)）的验收，也是整个项目的"物理可行性证明"。

**交付物**：
- [ ] 定时器 → ADC 采样 → 控制律 → PWM 更新的**硬件时间线**（[02 §2.5](02-embodied-ai-robot-profile.md#25-实时需求的量化)）
- [ ] `echo-driver`：电机控制外设驱动（定时器 TRGO / ADC / DMA / 高级定时器 PWM）
- [ ] FOC 电流环（在定时器 ISR 内执行，**不切上下文**）
- [ ] 编码器读取与位置/速度环
- [ ] `echo-bench`：**完整版**，报告 P50/P99/P99.9/max 分布 + CSV/JSON 导出
- [ ] `echo-bsp-stm32h7-joint`：单关节参考设计（MCU + 驱动板 + BLDC 电机）
- [ ] 一份**抖动分析报告**：各环的实测分布、瓶颈定位、与设计目标的差距

**验收标准（V1 单关节垂直切片）**：
1. **电机闭环运行**：BLDC 电机在电流环（≥ 10 kHz）+ 速度环（1 kHz）下稳定运行
2. **抖动实测**：1 kHz 速度环的周期抖动 **P99 < 5 µs**、P99.9 < 10 µs（示波器 + DWT 双重验证）
3. **无尖峰**：连续运行 1 小时，抖动分布**无长尾**（P99.9 与 P50 的差距 < 5 µs）
4. **ISR 内控制律可行**：电流环全程无上下文切换，实测中断延迟满足 [02 §2.5](02-embodied-ai-robot-profile.md#25-实时需求的量化) 的目标
5. **TCM 效果可量化**：控制律在 ITCM vs 在缓存 RAM 的抖动分布对比数据

> **第 5 项不是可选项。** [ADR-0018](05-design-decisions.md#adr-0018--内存分层tcm-放实时代码与数据缓存属性显式声明) 的价值需要数据支撑——如果实测发现 TCM 影响不大，那说明设计假设需要修正；如果影响很大，那这份数据就是后续所有优化的依据。**两种情况都必须先测出来。**

**风险**：
- 抖动达不到目标是最可能的结果，**这正是本里程碑存在的意义**——在投入数年之前发现它。
- 若 P99 显著超标，处置顺序：控制律入 ITCM → 栈入 DTCM → 关闭 D-Cache 对比 → 重新审视临界区 → 最后才考虑降低控制频率。

**这是阶段一的交付点。** 完成后应当能回答：**这个 RTOS 能不能用于实时控制？** 答案无论是"能"还是"不能，需要调整 X"，都比继续往下做更有价值。

## M8 · 现场总线 ★ 阶段二的起点

**规模**：L（CAN-FD）／ **XL+**（EtherCAT，见下）｜ **前置**：M7

**目标**：EchoOS 能协调多个节点。**这是"电机控制器"与"机器人操作系统"的分界点。**

**总线选型尚未确定**（[09 Q8](09-risks-and-open-questions.md#q8--现场总线选型--最高优先级)）。两条路径的差别极大：

| 路径 | 内容 | 规模 |
| --- | --- | --- |
| **A. CAN-FD**（建议起步） | 自研 CAN/CAN-FD 控制器驱动 + 协议层 + 简单同步帧 | **L** |
| B. EtherCAT 从站 | ETG 规范实现 + DC 分布式时钟 + 邮箱协议 + 一致性测试 | **XL+（2–4 年）** |

**交付物（以 CAN-FD 路径为例）**：
- [ ] `echo-can`：CAN-FD 控制器驱动（`echo-regs` 生成的寄存器 + 中断处理）
- [ ] `echo-fieldbus`：总线抽象 trait（**总线可替换是本里程碑的核心设计约束**）
- [ ] 报文定义层：固定布局的关节命令/状态帧（无序列化开销）
- [ ] `echo-bus-sync`：节点间时钟同步（CAN-FD 下目标 ~50 µs）
- [ ] 总线主站（协调节点）与从站（关节节点）两侧实现
- [ ] 错误处理：总线断开、节点丢失、报文超时

**验收标准**：
1. **双节点闭环**：协调节点以 1 kHz 向关节节点发送命令，关节节点回传状态，端到端延迟 < 200 µs
2. **同步精度**：两节点时钟偏差 < 50 µs，且不随时间漂移
3. **节点丢失检测**：拔掉一个节点，主站在 10 ms 内检测到并进入安全状态
4. **总线可替换性**：`echo-fieldbus` 的 trait 能在不改上层代码的前提下换成模拟后端（host 测试用）

**重要设计约束**：**总线抽象必须在 M7 就做对。** 若将来要从 CAN-FD 换到 EtherCAT，只应替换 `echo-fieldbus` 的实现，上层 `echo-motion` / `echo-safety` 一行不改。这是把 [风险 T18](09-risks-and-open-questions.md#910-具身智能机器人场景引入的新风险) 转化为可管理问题的唯一办法。

---

## M9 · 多关节协调 ★ 阶段二的终点

**规模**：XL ｜ **前置**：M8

**目标**：从"单关节控制"到"多关节协调运动"。

**交付物**：
- [ ] `echo-motion`：轨迹生成
  - 航点 → 高频设定点的插值（位置/速度/加速度连续）
  - 加加速度（jerk）限制，避免机械冲击
  - 多关节共享时间基准（与总线周期对齐）
- [ ] `echo-sensor`：同步采样（定时器 → ADC → DMA）与 IMU 融合
- [ ] 平衡/步态控制的最小实现（视机器人构型）
- [ ] `echo-bsp-stm32h7-coordinator`：协调节点参考设计
- [ ] 多关节测试台（≥ 3 个关节节点）

**验收标准（V2 双节点垂直切片）**：
1. **多关节同步**：所有关节的设定点在同一时间基准上，相位偏差 < 1 个控制周期
2. **插值连续性**：位置/速度/加速度曲线连续，加加速度有界（示波器实测，非仿真）
3. **闭环延迟**：协调节点命令 → 关节节点响应的端到端延迟 < 200 µs（1 kHz 总线）
4. **节点丢失处理**：拔掉一个节点，主站在 10 ms 内检测到并进入安全状态
5. **轨迹跟踪精度**：多关节联动轨迹的跟踪误差 < 设计指标

## M10 · AI 桥接与整机闭环 ★ 阶段三的起点

**规模**：L ｜ **前置**：M9

**目标**：打通"AI 栈 → 安全层 → 运动层 → 总线 → 关节"的完整链路，验证**端到端**的实时性与安全性。

**交付物**：
- [ ] `echo-bridge`：与 AI 栈的有界延迟接口
  - 固定布局无锁共享内存环（无序列化、无分配）
  - 序号 + 时间戳 + CRC + 版本协商
  - 传输后端：共享内存 / 以太网 / 串口（按 [Q11](09-risks-and-open-questions.md#q11--ai-侧硬件与通信方式) 确定）
- [ ] 一个**参考 AI 侧适配器**（跑在 Linux 上，演示协议与优雅降级）
- [ ] 整机联调：多关节 + 总线 + AI 命令流的完整闭环
- [ ] 故障注入测试框架

**验收标准**：
1. **端到端闭环**：AI 以 10 Hz 下发轨迹，机器人以 1 kHz 执行，全程无抖动尖峰
2. **故障注入**（核心验收项）：
   - AI 进程被 `kill -9` → 机器人平滑停止
   - 命令故意超限 → 被拒绝并记录，机器人不受影响
   - 通信丢包 30% → 仍能维持安全运行（降级）
   - 版本不匹配 → 拒绝连接，不崩溃
3. **接口稳定性**：AI 侧改协议只影响适配器，不影响 `echo-safety` 以下任何代码
4. **8 小时连续运行**：无内存增长、无抖动劣化

---

## M11 · 安全包络与命令仲裁 ★ 阶段三的核心

**规模**：L ｜ **前置**：M10

**目标**：实现 [ADR-0017](05-design-decisions.md#adr-0017--ai-命令是建议安全层是不可绕过的仲裁者) 的不变式——**AI 的输出是"建议"，安全层是不可绕过的仲裁者，且永远有一条当前安全轨迹在跑。**

> **为什么放在这里而不是更早**：安全包络的保证前提是**执行层行为可预测**（[ADR-0019](05-design-decisions.md#adr-0019--分阶段交付实时控制优先)）。M7 已经用数据证明了抖动水平，M8/M9 已经建立了确定性的总线链路——此时安全层的计算才有意义。

**交付物**：
- [ ] `echo-safety`：安全包络
  - 关节限位（位置/速度/加速度/加加速度/力矩）
  - 工作空间边界、自碰撞检查、奇异位形
  - 命令新鲜度与超时降级
  - 安全状态机：`INIT → READY → ACTIVE → DAMPING → FAULT → ESTOP`
  - **`validate` 是纯函数**（无副作用、无分配、无阻塞）→ 可在 host 上穷举测试
- [ ] `echo-motion` 的**失联降级路径**：无新命令时沿当前轨迹完成后平滑减速
- [ ] 故障注入测试框架
- [ ] `xtask lint-deps` 的单向链校验生效（[04 §4.4](04-crate-layout.md#44-依赖图)）

**验收标准**：
1. **安全包络拒绝测试**（核心验收项）：构造 6 类非法命令（超限、超时、跳变、奇异、越界、版本不符），**全部被拒绝且进入正确的降级状态**
2. **AI 失联测试**（核心验收项）：中断命令流，机器人从全速运行**平滑减速到停止**——用加速度计验证无冲击、无失控
3. **旁路检测**：故意在代码中加入绕过 `echo-safety` 的路径 → `cargo xtask lint-deps` 必须报错
4. **`validate` 的 host 测试覆盖率** ≥ 95%（纯函数，没有理由不做到）
5. **8 小时连续运行**：无抖动劣化、无内存增长

## M12 · 服务层（可选）

**规模**：XL ｜ **前置**：M9（可与 M10/M11 并行）

**目标**：EchoOS 具备完整的系统服务能力，可支撑真实产品原型。

**交付物**：
- [ ] `echo-fs`：日志结构文件系统（掉电一致性、磨损均衡）
- [ ] `echo-ota`：A/B 双分区升级、镜像校验、回滚
- [ ] `echo-shell`：完整版（任务、内存、定时器、互斥量、文件系统诊断）
- [ ] `echo-async`：阻塞原语的 `Future` 适配 + 可选执行器
- [ ] 长时间稳定性测试（7×24 小时运行 + 内存泄漏/碎片检测）
- [ ] 文档：用户指南、移植指南、API 文档

**验收标准**：
1. **掉电一致性**：在随机时刻断电 1000 次，文件系统可恢复且无数据损坏（QEMU 可模拟复位）
2. OTA 升级失败回滚：写入损坏镜像 → 自动回滚到旧版本
3. 7×24 小时运行：栈水位、内存池用量、定时器数量全部稳定（无泄漏）
4. 各服务可独立裁剪：`minimal` 配置下不含任何服务 crate，Flash 占用回到 M2 水平

## M13 · 用户态与系统调用（可选/长期）

**规模**：XL ｜ **前置**：M12

**目标**：非特权任务 + `SVC` 系统调用 + 能力模型。

**交付物**：
- [ ] `echo-sys`：系统调用号定义、`SVC` 陷入、参数校验
- [ ] 非特权任务：`CONTROL` 寄存器配置、独立 PSP 栈
- [ ] `UserPtr<T>`：用户指针校验（含 TOCTOU 防护）
- [ ] 类型化句柄 + 能力模型
- [ ] 系统调用边界的形式化测试 / fuzzing

**验收标准**：
1. 非特权任务无法直接访问内核内存（MPU 触发 `MemManage`）
2. 恶意系统调用参数（越界句柄、非法指针）被拒绝且不崩溃
3. 系统调用开销 < 1 µs
4. 能力模型：任务只能访问被显式授予的资源

**重要判断**：这一阶段**风险最高、收益最不确定**。系统调用边界是内核中唯一"Rust 类型系统完全不提供保护"的地方（[06 §6.7](06-subsystems.md#67-系统调用与用户态后期m8)）。**建议推迟到 M10 完成后重新评估需求**——若目标场景（工业控制 / 汽车 ECU）不需要多租户隔离，可以完全跳过，把精力投入实时性验证与认证材料。

**可并行的分支**（团队 > 2 人时）：

| 分支 | 内容 | 可并行于 |
| --- | --- | --- |
| 内核线 | M2 → M3 → M4 → M5 | — |
| 移植线 | RISC-V 移植（M6） | M5 |

| 阶段二预研 | 总线选型（[Q8](09-risks-and-open-questions.md#q8--现场总线选型--最高优先级)）、CAN-FD 控制器调研 | M5–M7 |

- [Q10（控制环频率与关节数）](09-risks-and-open-questions.md#q10--控制环频率与关节数) —— **影响 M7 的抖动验收指标**，建议在 M3 之前给出。

> **第 5 步是 L1 特有的前置验证，应尽早执行。** 若 SVD 生成在目标芯片上不可行，整个 L1 策略的基础就动摇了。
>
> **注意 M1 的规模已因 L1 决策从 S 上调为 L。** `svdgen` 与寄存器层是 L1 的入场费，无法绕过也无法推迟。好消息是它是**一次性投入**：生成器写对之后，后续每支持一颗新芯片的成本从"数月"降到"换一个 SVD 文件"。
