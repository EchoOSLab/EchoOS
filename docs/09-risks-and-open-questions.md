# 09 · 风险登记与待确认问题

## 9.1 技术风险

| # | 风险 | 影响 | 概率 | 缓解措施 | 触发信号 |
| --- | --- | --- | --- | --- | --- |
| **T1** | **★ L1 策略导致范围爆炸**——所有基础设施自研 | **极高** | **高** | 见下方的专门分析（§9.1.1）。核心缓解：**SVD 代码生成**（ADR-0015）消除最大的一块；服务层按需交付而非一次做全；**EtherCAT 见 [T18](#910-具身智能机器人场景引入的新风险)** | 出现"顺便把 X 也自研了吧"的提议，且 X 不在里程碑清单内 |
| T1b | 分阶段失控：M1 因寄存器层而无限期延长 | 高 | 中 | M1 内部严格按 `svdgen → 生成 → vcell/atomic → 启动 → UART` 的顺序，每步可独立验证；先只支持**一种中断和一个 UART**，其余外设按需生成 | M1 超过预期 2 倍仍未点亮串口 |
| T1c | 第三方驱动生态无法复用，用户迁移成本高 | 高 | **确定** | 接受这是 L1 的固有成本；`echo-hal` 保持与 `embedded-hal` 概念对齐；预留 `echo-hal-compat` 的设计空间 | 用户反馈"想把现有驱动移植过来太麻烦" |
| T2 | **实时性达不到目标**（临界区过长、ISR 过长） | 高 | 中 | M2 起建立延迟基准并每 PR 回归；临界区长度作为审查项；`echo-bench` + CI 守卫 | 基准劣化 > 10% 未被解释 |
| T3 | **上下文切换汇编的正确性** | 高 | 中 | 用 `echo-arch-mock` 把调度**决策**测透，让汇编只做机械搬运；栈 canary 验证帧边界；先做单任务 `SVC` 启动再上多任务 | 出现随机崩溃/难以复现的栈损坏 |
| T4 | **`Arch` trait 抽象泄漏或过度泛型化** | 中 | 中 | M6 用第二个架构做真实验证；若抽象失败，退化为"编译期固定单例 + 少量 `extern "Rust"`" | RISC-V 移植需要修改内核代码 |
| T5 | **多 crate + 多 target 构建复杂度过高** | 中 | 高 | `default-members` 分离 + `xtask` 统一入口；M0 先用最小 workspace 验证构建矩阵 | 开发者开始绕过 xtask 直接敲 cargo |
| T6 | **`unsafe` 代码引入 UB** | 高 | 中 | 按 crate 白名单（ADR/规则 R3）；Miri 覆盖 host 可测部分；每个 unsafe 块必须 `// SAFETY:` 注释；`cargo geiger` 基线守卫 | unsafe 行数上升；SAFETY 注释与实际不符 |
| T7 | **优先级反转的处理不完备**（传递性继承缺失） | 中 | 中 | 首版明确限制为**非传递**继承并在文档声明；M4 的测试用例显式覆盖该限制 | 出现三方反转的死锁报告 |
| T8 | **阻塞/唤醒竞态**（超时与事件同时到达） | 高 | 中 | `MockArch` 提供精确时间控制与交错注入，逐个构造竞态场景 | 偶发的任务"丢失唤醒" |
| T9 | **QEMU 与真机行为差异**导致测试通过但真机失败 | 中 | 高 | 明确区分"逻辑正确性"（QEMU）与"实时性绝对值"（真机）；M6 起建立周期性真机回归（HIL） | QEMU 绿但真机挂 |
| T10 | **Rust 生态版本漂移** | **无**（L1 下已消除） | — | 不再依赖任何上游 crate。仅受 `rustc` 版本影响 → 由 `rust-toolchain.toml` 固定 | 工具链升级不兼容 |
| T15 | **`svdgen` 生成错误**——生成器是信任根，错了则所有芯片的寄存器定义都错 | 高 | 中 | ADR-0015 的四类测试（解析/校验/快照/回环）；生成产物 check in 且 CI 守卫一致性；已知 SVD 缺陷写入补丁表而非改生成文件 | 出现"位域读出来是错的"类 bug |
| T16 | **`echo-atomic` 在 M0/M0+ 上的临界区模拟**可能破坏实时性（原子操作变成长临界区） | 中 | 中 | 首版只支持 M3+（有原生 CAS）；M0+ 作为后续降级目标并单独评估 | M0+ 上临界区窗口超阈值 |
| T17 | **自研 HAL 的 trait 设计不当**，后期发现无法表达某类外设 | 中 | 中 | 先用 2–3 个真实驱动（UART/SPI/I2C）验证 trait 设计；M6 的真机 BSP 是检验点 | 某外设需要改 trait 才能表达 |
| T11 | **FPU lazy stacking / TrustZone 等架构细节** | 中 | 中 | 分阶段：M2 无条件全保存（正确性优先），M5 再优化；TrustZone 留待将来 | 浮点任务出现数据损坏 |
| T12 | **单核假设限制多核 MCU** | 中 | 中 | 首版明确单核；`echo-critical` 预留自旋锁路径；多核以 AMP 方式各自运行实例 | 需要支持 ESP32 双核等场景 |
| T13 | **编译期静态配置缺乏直观性**，配置错误难发现 | 低 | 中 | BSP 提供带文档的常量模块；`const_assert!` 校验配置合法性 | 配置错误在运行期才暴露 |
| T14 | **单地址空间下子系统 bug 影响全系统** | 中 | 中 | MPU 纵深防御；子系统间通过类型化 API 隔离；关键数据结构加运行时不变式检查 | 一个子系统的 UB 导致系统崩溃 |

### 9.1.0 具身智能机器人场景引入的新风险

场景明确为具身智能机器人后（[02](02-embodied-ai-robot-profile.md)）新增的风险：

| # | 风险 | 影响 | 概率 | 缓解措施 | 触发信号 |
| --- | --- | --- | --- | --- | --- |
| **T18** | **★ EtherCAT 与 L1 策略冲突**——自研从站栈是 2–4 年工程，不做则无法控制人形机器人 | **极高** | **高** | 从 CAN-FD 起步并保持 `echo-fieldbus` 可替换；若必须 EtherCAT，采购协议栈并明确放宽 L1 的适用范围 | 需要支持高速人形且指定 EtherCAT |
| **T19** | **D-Cache 与 DMA 一致性 bug**——静默数据损坏，只在特定时序出现 | 高 | **高** | MPU 显式声明 cache 属性；DMA 缓冲区强制走非缓存区或显式 clean/invalidate API；M6 建立专项测试 | 出现"偶发的数据错乱"类 bug |
| **T20** | **抖动目标达不到**——D-Cache miss、总线争用、中断嵌套导致尖峰 | 高 | 中 | 控制律代码放 ITCM、栈放 DTCM；`echo-bench` 报告分布而非最大值；把抖动作为 CI 回归指标 | P99.9 显著高于 P50 |
| **T21** | **多速率调度错误**——相位漂移、槽位超限、任务间隐式依赖 | 高 | 中 | 静态调度表编译期生成 + `const_assert!` 校验；超限检测与钩子；host 上用 `MockArch` 精确验证相位 | 控制环出现周期性扰动 |
| **T22** | **安全层被绕过**（`echo-bridge` 与 `echo-safety` 之间出现反向依赖或旁路） | **极高** | 低 | `xtask lint-deps` 校验 `bridge → safety → motion → fieldbus` 单向链（[04 §4.4](04-crate-layout.md#44-依赖图)）；代码审查重点 | 出现"为性能直接下发命令"的改动 |
| **T23** | **无硬件验证条件**，抖动指标无法实测 | 高 | 中 | [Q13](#q13--是否具备硬件验证条件) 优先解决；最小双节点闭环系统 | M6 后仍无真机 |
| **T24** | **AI 侧接口频繁变更**，`echo-bridge` 反复重写 | 中 | **高** | 固定布局 + 版本协商；接口冻结后只做加法；把版本不匹配设计为**拒绝而非崩溃** | AI 团队每月改协议 |

> **T18 与 T22 是机器人场景下最需要关注的两条**：前者是可行性问题，后者是正确性问题。T18 见 [Q8](#q8--现场总线选型--最高优先级)，T22 已有 `lint-deps` 作为自动防线。

### 9.1.1 T1 专项分析：L1 策略的范围影响

[ADR-0014](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研) 的 L1 决策**是整个方案中最大的风险来源**，需要单独评估。

**被自研替换的组件及其规模**：

| 原依赖 | 自研替代 | 规模 | 是否有捷径 |
| --- | --- | --- | --- |
| `cortex-m`（寄存器+内在函数） | `echo-cortex-m-regs` + `echo-arch-cortex-m` | L | 规模小且稳定，手写可控 |
| 芯片 PAC（`stm32f4xx-hal` 等） | `echo-stm32f4-regs` 等 | **XL × 芯片数** | ★ **SVD 代码生成** |
| `vcell` | `echo-vcell` | S | 约 200 行 |
| `portable-atomic` | `echo-atomic` | S | M3+ 原生 CAS；M0+ 用临界区 |
| `heapless` | `echo-util` 的容器 | M | 按需实现，不必做全套 |
| `embedded-hal` | `echo-hal` | M | trait 数量有限 |
| `defmt` | `echo-trace` | M | 首版可用纯文本日志 |
| `smoltcp` | 自研协议栈 | **XL+** | ❌ 无捷径 → 通用 TCP/IP 已列为非目标 |
| **EtherCAT 从站协议栈** | 自研 | **XL+（2–4 年）** | ❌ **无捷径** → 见 [T18](#910-具身智能机器人场景引入的新风险) / [Q8](#q8--现场总线选型--最高优先级) |
| `probe-rs`（host 工具） | 无需替代 | — | ✅ 允许（不进镜像） |
| `cargo-binutils`（host 工具） | 无需替代 | — | ✅ 允许 |

**结论**：**除 EtherCAT 外，其余都有可控的落地路径**，且 SVD 代码生成把最大的一块（芯片 PAC）从"每月一颗芯片"降到"换一个文件"。

**唯一无法缓解的是 EtherCAT** —— 且它**恰好是**机器人场景最想要的总线。这是 L1 策略与目标场景的**正面冲突**，也是 [Q8](#q8--现场总线选型--最高优先级) 成为当前最高优先级问题的原因。

绕开它的方式有三条：**(a) 从 CAN-FD 起步**（推荐）、(b) 采购从站协议栈并放宽 L1 的适用范围、(c) 不使用 EtherCAT 类的高同步总线。三条都需要明确决策，不能默认。

**建议的止损线**：若 M2 结束时实际进度落后计划 3 倍以上，应重新评估 L1 决策（这是 ADR-0014 中列出的复议条件）。**提前定义止损线比事后争论更有效** —— 它把"要不要放宽 L1"从情绪化讨论变成对预设条件的客观检查。

| # | 风险 | 影响 | 概率 | 缓解措施 |
| --- | --- | --- | --- | --- |
| P1 | **范围过大**——OS 是多年工程，容易永远"还差一点就能用" | 高 | 高 | 严格限定 M0–M2 为"可演示的最小闭环"；M2 之后即产出可演示版本；每个里程碑必须可演示 |
| P2 | **与成熟生态竞争**——Embassy/RTIC 占据嵌入式 Rust，`ros2_control` 占据机器人 | 中 | 中 | 差异化已明确（[01 §1.5](01-vision-and-scope.md#15-echoos-的差异化定位)）：**AI 与硬实时之间的安全边界**（[ADR-0017](05-design-decisions.md#adr-0017--ai-命令是建议安全层是不可绕过的仲裁者)）。RTIC/Embassy 不做机器人语义，`ros2_control` 无硬实时保证且无隔离。**不与它们竞争实时性数字** |

| P4 | **缺乏真实硬件**，无法验证抖动指标 | 高 | 中 | [Q13](#q13--是否具备硬件验证条件)：M2 前准备 STM32H7 开发板（V1 切片用），M7 前补齐双节点系统 |
| P5 | **认证路径不清晰**——Rust 在 ISO 26262 / IEC 61508 下的认证实践不成熟 | 高 | 中 | G7 定位为"预留路径"而非"已认证"；文档化安全契约与可追溯性；关注 Ferrocene 等 Rust 认证工具链进展。**L1 在此是加分项**：无第三方依赖意味着无需对上游做认证论证 |
| P6 | **文档滞后于代码**，架构约束被悄悄破坏 | 中 | 高 | `cargo xtask lint-deps` 让架构约束**可执行**；PR 模板要求说明是否影响设计 |
| P7 | **吸引不到贡献者**——缺乏清晰的入门路径 | 低 | 中 | 序号化示例（`examples/01..08`）；`good-first-issue` 标签；文档先行 |
| P8 | **过早优化**——在没有基准的情况下优化延迟 | 中 | 中 | 先建基准（M2），再谈优化；优化必须有基准数据支撑 |

## 9.3 待确认问题

这些问题会**实质性地改变设计方案**，需要在开工前确定。

### Q1 · 首选目标平台是哪个？ 【⏩ 已由 Q9 取代】

> 目标场景明确为具身智能机器人后，此问题由 [Q9](#q9--硬件平台--最高优先级) 取代——候选平台已从"通用 MCU"收窄为机器人场景的实际选择。以下内容保留作背景。

**影响**：决定 M1/M2 的全部技术选型（启动代码、向量表、时钟源、移植层实现）。

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. QEMU Cortex-M3 (mps2-an385) 首选，STM32F401RE 真机** | QEMU 可脚本化进 CI；STM32F4 生态最成熟、资料最多；Cortex-M 是嵌入式主流 | 需要买板子（约 ¥100） |
| B. QEMU RISC-V virt 首选 | RISC-V 是趋势；QEMU 支持好 | 真机生态与调试体验弱于 Cortex-M |
| C. ESP32-C3（RISC-V） | 有 WiFi/BLE，IoT 场景完整 | 外设复杂、工具链特殊、启动流程不标准 |
| D. 手头已有的硬件 | 零成本 | 可能是冷门芯片，生态支持差 |

**建议：A**。理由：Cortex-M 是嵌入式 RTOS 的主战场，生态与调试工具最成熟，QEMU 支持完善，STM32F4 是最容易获得帮助的平台。RISC-V 在 M6 作为**可移植性验证的第二个架构**引入（这恰好也是它最大的价值所在——不是为了支持 RISC-V，而是为了证明抽象没泄漏）。

**需要你回答**：是否有现成硬件？愿意采购哪块？

### Q2 · "从零开发"的边界在哪里？ 【✅ 已决定：L1】

**决定（2026-09-22）**：采用 **L1 —— 完全裸写，零外部 crate 依赖**。

| 层次 | 含义 | 相对工作量 | 状态 |
| --- | --- | --- | --- |
| **L1 完全自研** | `[dependencies]` 中外部 crate 恒为 0 | ×10 | ✅ **选定** |
| L2 复用架构封装 | 复用 `cortex-m`，自研内核逻辑 | ×1（基准） | ❌ 未采用 |
| L3 复用 `cortex-m-rt` 运行时 | 直接用现成启动流程 | ×0.6 | ❌ 与 RTOS 需求冲突 |
| L4 包装现有 RTOS | FreeRTOS/Zephyr 封装 | ×0.2 | ❌ 违背"从零" |

**落地方式**：
- 见 [ADR-0014](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研)（策略）与 [ADR-0015](05-design-decisions.md#adr-0015--寄存器定义通过自研-svdgen-代码生成)（使能条件）
- 依赖边界精确定义见 [01 §1.7](01-vision-and-scope.md#17-依赖边界l1-完全自研)：**编译工具链与 host 侧工具允许，第三方 Rust crate 禁止**
- 执行保障：依赖规则 **R7** + `cargo xtask lint-deps`（[04 §4.5](04-crate-layout.md#r7--零外部-crate-依赖-)）

**必须接受的三项成本**（已记录在案，不重复讨论）：

1. **工期延长约一个数量级** —— 主要发生在 M1（寄存器层入场费）与 M6（自研 HAL + 驱动）
2. **第三方 `embedded-hal` 驱动无法直接使用** —— 这是**长期成本**，不是一次性成本
3. **总线选型未定** —— 这是当前最高优先级问题（[Q8](#q8--现场总线选型--最高优先级)），不再是可以推迟的"服务层"问题

**关键前提**：`svdgen`（SVD 代码生成器）必须按 ADR-0015 实施。**若跳过它改用手写寄存器，M1 将从数周变成数月，且每支持一颗新芯片都要重复付出** —— 此时 L1 实际上不可行。

**复议条件**：M2 结束时进度落后计划 3 倍以上，或目标场景明确要求 IP 网络。

### Q3 · 目标应用场景是什么？ 【✅ 已决定：具身智能机器人】

**决定（2026-09-22）**：**具身智能机器人**——人形 / 四足 / 协作机械臂 / 移动机器人。EchoOS 运行在**小脑层（协调）与脊髓层（关节执行）**，不做大脑层（AI 推理 / SLAM / 规划）。

完整场景分析见 [02-embodied-ai-robot-profile.md](02-embodied-ai-robot-profile.md)。该分析**修正了本文档多处结论**（网络非目标被推翻、抖动指标新增、Cortex-M7/D-Cache 成为必答题、新增机器人专用 crate）。

以下为原始分析，保留作背景。



**影响**：决定是否需要认证材料、是否需要 MPU 隔离、是否值得做 M8（用户态）。

| 场景 | 关键需求 | 对设计的影响 |
| --- | --- | --- |
| 工业控制（PLC/电机/网关） | 硬实时、长周期可靠 | 当前设计直接适配 |
| 汽车电子（ECU/BMS） | ISO 26262 认证 | 需要可追溯性、安全契约文档、M8 的隔离 |
| 高端 IoT | 网络 + FS + OTA | 需要强化 M7；实时性要求可放宽 |
| 航空航天 | DO-178C | 需要形式化验证投入，当前设计需大幅增强 |
| 学习/研究/个人项目 | 完整性、可读性 | 可跳过 M8，强化文档与示例 |

**建议**：先按"工业控制 + 高端 IoT"设计（当前方案已覆盖），把认证作为 G7（预留路径）而非近期目标。

### Q4 · 是否需要 MPU 隔离？ 【中优先级】

**影响**：Cortex-M0+（无 MPU 或仅 8 region）与 M3/M4/M33 的选型；M5 的范围。

- 若目标是 **Cortex-M3/M4 及以上** → MPU 可用，按 [ADR-0005](05-design-decisions.md#adr-0005--单地址空间--mpu-静态分区) 实施
- 若需要覆盖 **Cortex-M0/M0+** → 只能退化保护（canary + 类型系统），需明确取舍

**建议**：M3/M4 起步，M0+ 作为后续的降级目标。

---

### Q5 · 是否需要 SMP？ 【中优先级】

当前设计明确假设单核。若目标是 ESP32（双核 Xtensa/RISC-V）或 RP2040（双核 M0+），需要重新设计调度器（per-core runqueue、IPI、跨核同步）。

**建议**：首版单核。多核以 AMP 方式支持（每核一个 EchoOS 实例，通过共享内存 + 邮箱通信）。

---

### Q6 · 许可协议？ 【低优先级但需定】

建议 `MIT OR Apache-2.0`（Rust 生态惯例，与所有依赖一致）。需要放置 `LICENSE-MIT` / `LICENSE-APACHE`。

---

### Q7 · 项目人力与时间预期？ 【中优先级】

- 单人兼职 vs 单人全职 vs 小团队 → 直接决定 M7/M8 是否可行
- 若为单人项目，建议**明确砍掉 M7 的大部分**（FS/OTA 按需做，网络推迟甚至不做），集中把 M2–M6 做扎实。**在 L1 下这一点比 L2 方案更关键**——没有生态可以借力，人力就是硬约束

---

### Q8 · 现场总线选型？ 【★ 最高优先级】

**影响**：决定项目最难的一块是否在范围内，也决定 [ADR-0014](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研) 的 L1 策略是否需要调整适用范围。

背景见 [02 §2.9](02-embodied-ai-robot-profile.md#29-现场总线为什么它是关键路径-阶段二)。核心矛盾：

| 选项 | 同步精度 | 自研难度 | 与 L1 的关系 | 机器人适用性 |
| --- | --- | --- | --- | --- |
| **A. EtherCAT 从站** | **< 100 ns** | ❌ **2–4 年**（ETG 规范 2000+ 页 + DC 时钟 + 一致性测试） | ❌ 直接冲突 | 人形机器人事实标准 |
| **B. CAN-FD** | ~50 µs | ✅ 3–6 个月 | ✅ 符合 | 四足、机械臂、低成本人形 |
| **C. 自定义高速串口** | ~1 µs | ✅ 可行 | ✅ 符合 | 部分自研机器人 |
| **D. EtherCAT + 采购从站协议栈** | < 100 ns | ✅ 数月集成 | ⚠️ 需放宽 L1 | 工业主流做法 |

**我的建议**：**B 或 C 起步，把总线做成可替换的抽象层**（`echo-fieldbus` 已经是这么设计的）。理由：

1. **CAN-FD 的 50 µs 同步精度对四足、机械臂、中低速人形足够**，且完全自研可行。
2. EtherCAT 的 < 100 ns 只有高速人形 / 高动态运动才真正需要。
3. **从 CAN-FD 起步可以保持 L1 完整**，并把最难的问题推迟到有真实需求时再决策。
4. 若最终必须 EtherCAT，**建议采购从站协议栈而非自研** —— 这不是"操作系统"问题，是外部标准的实现问题（[02 §2.9](02-embodied-ai-robot-profile.md#29-现场总线为什么它是关键路径-阶段二)）。

**需要你回答**：目标机器人的类型与动态性能要求？是否已有指定总线（例如团队已选定 EtherCAT）？

---

### Q9 · 硬件平台？ 【★ 最高优先级】

| 选项 | 说明 | 影响 |
| --- | --- | --- |
| **A. STM32H743/H745**（Cortex-M7 @480 MHz） | 关节控制器与协调节点的主流选择；带 D-Cache + TCM | 引入 [02 §2.8.3](02-embodied-ai-robot-profile.md#283-缓存与-tcmcortex-m7-的现实-阶段一) 的全部复杂度 |
| B. STM32G4（Cortex-M4F） | 电机控制专用（内置运放/比较器） | 无 D-Cache，简单；算力有限 |
| C. Jetson Orin 的 Cortex-R5F 安全岛 | 与 AI 同 SoC，共享内存通信 | 需新增 `echo-arch-cortex-r`；战略价值高 |
| D. 国产 MCU（RISC-V） | 供应链考量 | 需先验证 SVD 质量（影响 [假设 A7](#94-需要重点验证的假设)） |

**建议**：**A 起步**（生态与 SVD 质量最好），C 作为中期战略方向。注意 A 会把 D-Cache/TCM 复杂度提前引入——这是必要的，机器人场景绕不开。

---

### Q10 · 控制环频率与关节数？

决定抖动预算与总线带宽。需要具体数字：

- 电流环频率？（10 / 20 / 40 kHz）
- 关节数量？（12 / 23 / 40+）
- 是否有力控 / 阻抗控制需求？

---

### Q11 · AI 侧硬件与通信方式？

| 方案 | 延迟 | 复杂度 |
| --- | --- | --- |
| 同 SoC + 共享内存（Orin 安全岛） | **µs 级** | 高（需 Cortex-R 移植） |
| 独立 MCU + 以太网 | ms 级 | 中 |
| 独立 MCU + 串口 / CAN | ms 级 | 低 |

决定 `echo-bridge` 的传输后端设计（[02 §2.8.1](02-embodied-ai-robot-profile.md#281-ai-与硬实时的边界安全包络与命令仲裁--阶段三)）。

---

### Q12 · 是否需要功能安全认证？

SIL2 / PLd 等级会显著改变开发流程、文档要求与验证投入。若不要求认证，可精简流程（但仍建议保留需求→测试的可追溯性）。

---

### Q13 · 是否具备硬件验证条件？

机器人验证需要：MCU 开发板 + 电机驱动器 + 电机 + 总线设备 + 示波器/逻辑分析仪。**成本不低，但没有硬件就无法验证抖动指标**——而抖动是本项目的核心目标（[02 §2.5](02-embodied-ai-robot-profile.md#25-实时需求的量化)）。

**建议的最小验证系统**：2 块 STM32H7 开发板 + 2 个 BLDC 电机 + 驱动板 + CAN-FD 收发器，构成"双节点闭环"。

## 9.4 需要重点验证的假设

以下假设如果被证伪，方案需要调整：

| # | 假设 | 验证方式 | 验证时机 |
| --- | --- | --- | --- |
| A1 | `Arch` trait 抽象足以覆盖 Cortex-M 与 RISC-V 的差异，且不泄漏 | M6 的第二个移植 | M6（**最晚**） |
| A2 | 单地址空间 + 类型系统能提供足够隔离，不需微内核 | 代码审查中统计"类型系统拦下的问题" vs "需要运行时检查的问题" | M5 |
| A3 | `BASEPRI` 临界区方案在实际中断负载下确实优于 `PRIMASK` | 两种方案都实现，用 `echo-bench` 对比 QEMU/真机的延迟 | M4 |
| A4 | 线程模型（非 async）不会导致任务数量爆炸（栈占用可接受） | M3–M4 的实际用例栈水位统计 | M4 |
| A5 | QEMU 上的逻辑测试能有效预测真机行为 | M6 真机回归的失败率 | M6 |
| A6 | 约 42 个 crate 的规模可通过 `xtask` 有效治理 | M0–M2 的实际开发体验 | M2 |
| **A7** | **★ SVD 代码生成能覆盖目标芯片的寄存器需求**（含 `derivedFrom` 继承、数组寄存器、厂商 SVD 的不规范之处） | 用 STM32F401 的完整 SVD 跑通生成 → 编译 → 点亮 UART | **M1（最晚）** |
| **A8** | **★ L1 策略的总工作量在可承受范围内** | M2 结束时的进度对比计划 | **M2（止损线）** |

> **A7 是 L1 的成败关键。** 若 SVD 生成不可行（例如目标芯片的 SVD 质量太差），L1 就退化为"手写寄存器"，此时 [ADR-0014 的复议条件](05-design-decisions.md#adr-0014--零外部-crate-依赖l1-完全自研)应当被触发。
>
> **A8 是止损线。** 提前定义它，把"要不要放宽 L1"从情绪化讨论变成对预设条件的客观检查。

## 9.5 下一步行动清单

按顺序执行：

1. **【仍阻塞】确认 §9.3 的 Q1（首选平台）** —— Q2 已决定为 L1，但首选平台未定，它决定 M1 的第一块 SVD 用哪个芯片
2. 补齐工具链（[07 §7.1](07-toolchain-and-testing.md#71-当前环境状态)）
3. 用**最小 workspace**（4 个 crate：`echo-util` + `echo-vcell` + `echo-arch-api` + `echo-arch-mock`）验证构建矩阵能否与交叉 target 共存
4. 编写 `echo-arch-api` 的 `trait Arch` 初稿 —— 这是最重要的接口契约
5. **★ 在最小 workspace 上先跑通 `svdgen` 的骨架**（解析 + 生成一个外设），验证 A7 —— **这是 L1 的第一个技术风险点，越早暴露越好**
6. 铺开完整 workspace 结构 + `xtask` + CI（M0）
7. 进入 M1

> **第 3 步不可跳过。** 多 crate + 多 target 的构建配置是嵌入式 Rust 项目最容易卡住的地方，先用最小规模验证，比在 42 个 crate 上调试便宜得多。
>
> **第 5 步是 L1 特有的前置验证。** 在铺开完整结构之前先证明"寄存器可以自动生成"，避免在错误的假设上投入数月。
